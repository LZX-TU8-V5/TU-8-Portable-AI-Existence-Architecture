## 一、协议设计

### 两层架构

```
定义层 (Definition Layer)
├─ 性质：纯代数封闭，状态演化规则，可形式化验证
├─ 约束：零超越数（math.cos/sin/pi/exp/log 等禁止）
├─ 输出：代数常数表（_BALL_TRIG / _TRIG_360 / _SPHERE_DIRECTIONS）
└─ 文件：只含预计算数据，无运行时计算

        ↓ 隔离层（Anti-Corruption Layer）

执行层 (Evaluation Layer)
├─ 性质：开放世界，允许 π 作为高效翻译官
├─ 约束：无（可自由使用 math.*）
└─ 角色：计算加速 / 渲染 / IO
```

### π-可擦除性判断

```
把 π 换成符号 P，最后一步能否通过代数恒等式消掉？

能消掉  → 安全的计算加速（语法糖）  ✅
不能消掉 → 状态污染（需重构）       ❌
```

### 初始化函数白名单

以下函数允许含超越数（启动时一次性调用，非热路径）：
- `_build_trig_table` — orb_ring 三角预计算表
- `_build_trig_table_360` — orb_ps 360° 三角表
- `_build_sphere_directions` — topology_connector 球面方向采样

## 二、核心工程设计

### 深度追踪 Visitor

关键问题：嵌套调用时如何正确判断"热路径内/外"？

```
refresh()                        ← 热路径（depth=1）
  └─ _ball_xy_by_name()         ← 嵌套函数（depth=1，不重置）
       └─ _BALL_TRIG[...]

_build_trig_table()              ← 初始化函数（depth=0）
  └─ math.cos(rad)               ← 允许（depth=0）
```

解决方案：使用 `_hot_depth` 计数器（而非函数名）
- 进入热路径函数 → depth += 1
- 退出热路径函数 → depth -= 1
- 嵌套辅助函数不重置 depth（因为仍然在热路径作用域内）
- 违规判断：`_hot_depth > 0` = 热路径内

### 函数栈 vs 深度

| 属性 | 用途 |
|------|------|
| `_func_stack` | 追踪当前函数上下文（用于 violation 归属） |
| `_hot_depth` | 追踪热路径嵌套深度（用于判断是否热路径） |
