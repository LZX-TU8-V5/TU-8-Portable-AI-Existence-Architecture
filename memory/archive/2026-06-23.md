## SAG vs TU-8 索引系统深度对比（10:55-11:00）

### SAG核心数据模型（从001_init.sql提取）

**6张核心表：**
1. sources — 项目/租户（tenant_id + name + metadata JSONB）
2. documents — 文档（source_id FK, title, content, status, parse_status）
3. document_sections — 文档切片（document_id FK, heading, content, token_count）
4. source_chunks — 知识块（embedding vector(1024), search_text tsvector, rank, references UUID[]）
5. entities — 实体（type, name, normalized_name, embedding, 多种值类型int/numeric/datetime/bool/enum）
6. events — 事项（chunk_id FK, parent_id自引用, title/summary/content, keywords[], start_time/end_time, title_embedding + content_embedding）
7. event_entities — 事项↔实体关联（weight, embedding, 多对多桥表）

**关键索引策略：**
- 全文检索：tsvector GIN索引（search_text）
- 向量检索：HNSW索引（pgvector, cosine_ops）
- 三字模糊：pg_trgm扩展
- 实体精确：unique index on (source_id, type, normalized_name)

### SAG检索管线（从search-service.ts提取）

**multi模式8步管线：**
1. 查询向量化 → queryEmbedding
2. 实体召回（fast=BM25全文匹配 / standard=LLM抽取+名称精确+向量召回）
3. 实体→事件关联 → getEventIdsByEntityIds
4. 标题向量召回事件 → searchEventsByTitleVector
5. 合并种子事件 → unique(entityEvents + queryEvents)
6. 事件扩展（多跳）→ expandFixedHops / expandOneHop+expandDynamic
7. 粗排 → coarseRankEventsByContent（内容向量相似度）
8. 精排 → rerank model / LLM rerank → 回取关联切片

**多跳扩展策略：**
- multi：固定maxHops跳（expandFixedHops）
- hop：1跳+动态扩展（expandOneHop → expandDynamic）
- hopllm：1跳+LLM筛选+动态扩展

### TU-8 当前索引系统 vs SAG 对比

| 维度 | SAG | TU-8当前 | 差距 |
|---|---|---|---|
| **数据模型** | PostgreSQL 6表+7索引+pgvector | Markdown文件+JSON索引+O(N)遍历 | 🔴 本质差距 |
| **实体表示** | normalized_name+多值类型+embedding | 知识图谱Markdown节点(乱码) | 🔴 无法做精确查询 |
| **事项卡片** | events表(title/summary/content/keywords/time/embedding×2) | 奇点循环CycleRecord(有复盘但无embedding) | 🟡 结构有但缺向量化 |
| **关联关系** | event_entities桥表(weight+embedding) | Mermaid图(乱码不可用)+跨域连线表 | 🔴 无法程序化查询 |
| **检索方式** | BM25+向量+SQL多跳+Rerank | O(N)文本遍历+语义memory_search | 🔴 效率差3个数量级 |
| **增量更新** | 逐条INSERT+自动tsvector | 一次性批量生成,之后不更新 | 🔴 索引是死数据 |
| **租户隔离** | tenant_id默认值 | 无,全局共享 | 🟡 百条规模不需要 |
| **图谱可视化** | React D3交互图 | Mermaid静态图(乱码) | 🔴 不可用 |

### SAG 能吸收的5个核心点

1. **事项卡片(Event)模式** — SAG的chunk→event→entities三层结构是精髓。TU-8的CycleRecord已经接近event概念，但缺少：
   - normalized_name（实体归一化：	u8_memory=TU8_Memory=记忆系统应该合并）
   - keywords[]（关键词索引，替代全文tsvector）
   - embedding（向量化，用于语义召回）
   吸收方案：给CycleRecord和ExperienceCard加embedding字段，入库时自动向量化

2. **实体桥表(event_entities)** — SAG用weight+embedding的多对多桥表连接event和entity。
   TU-8的KNOWLEDGE_GRAPH.md里已有跨域连线概念，但无法SQL查询。
   吸收方案：用SQLite桥表替代Markdown图谱（最小改动：knowledge_graph.db, 单表event_entities）

3. **BM25+向量双路召回** — SAG的fast模式：BM25匹配实体→关联事件→扩展→rerank。
   TU-8的memory_search是纯向量，缺BM25精确匹配。
   吸收方案：给memory_search加BM25前置（对标题/标签做精确匹配，miss再走向量）

4. **增量入库+自动tsvector** — SAG的search_text是GENERATED ALWAYS AS，写入时自动维护。
   TU-8的INDEX.json是手工批量生成。
   吸收方案：写一个钩子，每次新增memory文件时自动更新INDEX.json和embedding

5. **多跳扩展(expandFixedHops)** — SAG的实体→事件→新实体→新事件循环扩展。
   TU-8的跨域连线表有同样逻辑但无法程序化执行。
   吸收方案：在SQLite桥表上实现2-hop扩展（1跳在百条规模足够）

### SAG 不适合TU-8的3个点

1. **PostgreSQL重依赖** — TU-8是单机Agent,加PostgreSQL是过度工程。SQLite+FTS5足够百条规模。
2. **TypeScript全栈** — TU-8核心是Python,引入TS增加维护负担。
3. **文档入库范式** — SAG面向"上传文档→切块→抽实体",TU-8的记忆是Agent运行时自产的,格式不同。

### 结论：吸收思想,不引入系统

SAG的核心洞察是：**结构化事项+实体索引+多跳扩展 > 纯向量检索**
TU-8应该吸收这个洞察,但用SQLite实现而非PostgreSQL：
- knowledge_graph.db: events表+entities表+event_entities桥表
- FTS5替代tsvector
- sqlite-vss替代pgvector(或直接用numpy余弦)
- 2-hop扩展替代maxHops多跳
