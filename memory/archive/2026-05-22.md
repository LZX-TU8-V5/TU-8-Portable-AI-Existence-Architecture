### 关键算法笔记
- **Recency衰减**：e^(-λ·age)，λ=ln2/halfLife，默认半衰期14天
- **Consolidation**：0.55·spacing + 0.45·span，spacing=clamp(log₁₊₊(N-1)/log₁₊₊(4))
- **PhaseBoost**：light=log₁₊₆(hits)/log₁₊₆(6)·recency + rem同理
- **MMR重排**：score = λ·sim(q,d) - (1-λ)·max_sim(d,S)，平衡相关性与多样性
- **混合检索**：向量搜索+BM25关键词→merge+时间衰减
- **去重**：95%余弦相似度阈值
- **安全**：prompt注入正则检测+XML实体转义

## OpenClaw LCM（无损上下文管理）压缩系统逆向（16:47-16:55 GMT+8）

### 本轮分析4个文件

#### 1. compact-Bt3jy8AS.js（45KB，17函数）- 压缩主入口
- `classifyCompactionReason`：分类压缩原因（no_compactable/below_threshold/already_compacted/live_context_exceeds/guard_blocked/summary_failed/timeout/provider_4xx/provider_5xx）
- `compactEmbeddedPiSessionDirect`：嵌入式PI会话直接压缩
- `summarizeCompactionMessages`：压缩消息摘要
- `truncateSessionAfterCompaction`：压缩后截断会话
- `hardenManualCompactionBoundary`：手动压缩边界硬化
- `replaceLatestCompactionBoundary`：替换最新压缩边界
- `serializeSessionFile`：会话文件序列化（JSONL格式，每行一个entry）

#### 2. compaction-runtime-context-BJ7wNksP.js（232KB，282函数）- 压缩运行时核心
**分阶段摘要流程（核心算法）**：
```
summarizeInStages (入口)
  ↓ 判断：消息数<4 或 总token≤maxChunkTokens → 直接摘要
  ↓ 否则：splitMessagesByTokenShare → 分2份(DEFAULT_PARTS=2)
  ↓ 每份 → summarizeWithFallback → summarizeChunks
  ↓    ↓ chunkMessagesByMaxTokens → 按token预算分块
  ↓    ↓ 每块 → generateSummary (LLM调用)
  ↓    ↓ 重试3次(500ms-5s延迟, 20%抖动)
  ↓ 合并所有部分摘要 → 再调summarizeWithFallback(用MERGE_SUMMARIES_INSTRUCTIONS)
  ↓ 如果失败 → 去掉超大消息再试
  ↓ 再失败 → 返回"Context contained N messages. Summary unavailable."
```

**摘要结构模板（5个必填节）**：
```markdown
## Decisions
## Open TODOs
## Constraints/Rules
## Pending user asks
## Exact identifiers
```

**合并摘要指令（MERGE_SUMMARIES_INSTRUCTIONS）**：
- 必须保留：活跃任务状态、批量操作进度、最后用户请求、决策与理由、TODO/约束、承诺/后续
- 优先保留近期上下文而非旧历史

**标识符保留策略**：
- policy="strict"：UUID/Hash/URL/路径/端口全部精确保留
- policy="off"：仅按需保留
- policy="custom"：自定义指令

**摘要质量审计（auditSummaryQuality）**：
- 检查5个必填节是否存在
- 检查关键标识符是否保留
- 检查最新用户请求是否在摘要中体现（hasAskOverlap关键词重叠检测）

**上下文裁剪（pruneContextMessages）**：
- 两级策略：softTrim（软裁剪工具结果）→ hardClear（硬清除工具结果为placeholder）
- 软裁剪：当ratio > softTrimRatio时，对可裁剪工具结果进行softTrimToolResultMessage
- 硬清除：当ratio > hardClearRatio时，将工具结果替换为placeholder文本
- 保留最近N个assistant消息（keepLastAssistants）

**消息分块（splitMessagesByTokenShare）**：
- 按token份额均分，但保持toolCall-toolResult配对完整
- 跟踪pendingToolCallIds，不在配对中间切割

#### 3. context-window-guard-DDsEyDd1.js（6函数）- 上下文窗口守卫
- `CONTEXT_WINDOW_HARD_MIN_TOKENS = 16000`（硬性最低）
- `CONTEXT_WINDOW_WARN_BELOW_TOKENS = 32000`（警告阈值）
- `resolveContextWindowInfo`：优先级 modelsConfig > model参数 > default(200K)
- 支持`agents.defaults.contextTokens`配置上限
- 本地/自部署模型低于32K时警告

#### 4. model-context-tokens-BRdBKZTD.js（11.5KB，19函数）- 压缩检查点与钩子
- **检查点机制**：压缩前创建session文件快照（checkpoint），最多保留25个/会话
- `captureCompactionCheckpointSnapshot`：copyFileSync创建快照
- `persistSessionCompactionCheckpoint`：写入sessionStore，记录reason/tokensBefore/tokensAfter/summary
- **压缩原因分类**：manual / timeout-retry / overflow-retry / auto-threshold
- **压缩后副作用**：
  1. emitSessionTranscriptUpdate（发送transcript更新事件）
  2. syncPostCompactionSessionMemory（post-compaction记忆同步，默认async模式）
- **钩子系统**：before_compaction / after_compaction，记录消息数/token数/压缩数/摘要长度

### 核心设计思想（可借鉴）
1. **渐进式容错**：全文摘要→去超大消息再试→返回默认文本，三层降级
2. **分而治之**：长对话先分块摘要再合并，避免超长context导致质量下降
3. **质量审计闭环**：摘要生成后自动检查必填节+标识符+用户请求覆盖
4. **检查点+回滚**：压缩前创建快照，最多25个，支持灾难恢复
5. **两级裁剪**：先软裁剪（保留摘要），再硬清除（替换为placeholder），尊重上下文窗口预算
6. **关键词重叠检测**：确保最新用户请求在摘要中有体现，防止"摘要丢了用户在问什么"
