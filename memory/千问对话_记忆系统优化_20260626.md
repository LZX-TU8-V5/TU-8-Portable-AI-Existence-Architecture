## 第1段：Soul 注入 vs 外部注入（双轨并行）

### 问题
"这个回复是在 Soul 注入么？还是除了 Soul 注入之外也得有注入？"

### 千问回答

**结论**：绝对不能只靠 Soul 注入，必须采用**Soul 注入 + 外部显式注入**的双轨并行机制。

#### 什么是 Soul 注入？
- 大模型底层的参数化记忆（Parametric Memory）+ 系统级提示词（System Prompt）
- 决定 AI 的"人设"、基础价值观、对话风格
- **致命缺陷**：静态、滞后。无法在对话中途"自我改写"底层灵魂

#### 为什么必须加外部显式注入？
- 充当大模型的**工作记忆（Working Memory）**
- 把刚发生、还没沉淀进 Soul 的"鲜活事实"塞进当前上下文
- 每次新对话发起时，中间件去本地记忆卡捞出浓缩摘要，拼在 System Prompt 最前面

#### 双轨协作流程

```
Step 1：新对话开启
  最终 Prompt = [Soul注入(人设/偏好)]
              + [外部注入(刚生成的浓缩记忆卡)]
              + [用户新消息]

Step 2：AI 思考与回复
  AI 既知道"你是谁"（Soul）
    又知道"刚才发生了什么"（外部注入）

Step 3：回复结束后的"沉淀"
  AI 回复 → 后端拦截记忆浓缩块
    → 废话丢弃 / 干货写入本地记忆卡
    → 下一轮通过"外部注入"喂给 AI
```

### 架构定位

| 机制 | 角色 | 对应人脑结构 |
|------|------|-------------|
| Soul 注入 | 定调子、人格、长期偏好 | 大脑皮层（性格） |
| 外部注入 | 记事实、鲜活上下文 | 海马体（工作记忆） |

### 设计结论
- Soul 注入负责"定调子"
- 外部注入负责"记事实"
- 两者结合 = 稳定人格 + 过目不忘

## 第2段：双轨注入解决模型漂移 + 压缩衰减

### 问题1
"我的意思是记忆模板得注入是在 Soul + 外部节律的注入，可以解决换 Auto 换模型和时间长了压缩后丢失偏移？"

### 千问回答

**结论**：是的！这是 Agent 记忆架构的"终极防御形态"。

#### 两大痛点
| 痛点 | 术语 | 根因 |
|------|------|------|
| Auto 模式换模型 | 模型漂移（Model Drift） | 新模型不理解老模型的复杂指令 |
| 时间长压缩丢失 | 压缩衰减（Compression Decay） | 有损压缩抹去早期细节 |

#### 双轨注入如何解决？

**对抗模型漂移**：
- 记忆模板写死在外部注入（System Prompt 头部）
- 无论底层怎么切模型，新模型接手第一个瞬间看到的就是硬塞给它的规则
- **被迫遵守模板，保证输出格式绝对一致**

**对抗压缩衰减**：
- 外部节律注入每次新对话触发 L1 时，把本地记忆卡的浓缩摘要"打补丁"贴到脑门上
- 大模型不需要回忆，只需要"阅读"你喂给它的笔记
- **把"回忆问题"变成"阅读理解问题"**，彻底杜绝丢失和偏移

#### 终极公式
```
[最终 Prompt] =
  [Soul 注入] (我是谁，性格，长期偏好)
  +
  [外部节律注入] (记忆模板强制指令 + 刚发生的浓缩记忆块)
  +
  [用户当前消息]
```

### 问题2
"Soul 注入机制是咋样的？是后台每轮都在注入？"

### 千问回答

**结论**：是的，Soul 注入是后台**每轮**都在注入的。

#### 为什么必须每轮注入？
- 大模型本身完全无状态（Stateless）
- 像一个每次聊完天就会立刻失忆的人
- 必须在每次准备回复时，把完整背景信息重新喂给它

#### 注入时机
用户发送新消息 → 经过"消息编译器" → 读取 Soul 配置 → 作为 System Prompt 一部分注入

#### 注入格式（标签化隔离）
```
<hero_soul>
[这里是你自定义的 Soul 核心内容、价值观和边界]
</hero_soul>
```
防止模型把"人设指令"和"用户聊天内容"搞混

#### 注入优先级
- 最高级别（宪法地位）
- 加载顺序在普通功能指令之前
- 用户指令与 Soul 边界冲突 → 优先遵循 Soul

#### 心理学视角
- 类似"启动效应（Priming Effect）"
- 预先呈现的信息直接影响后续信息处理方式
- 让模型自动规避"客服腔"，表现出设定的人设

#### 完整工作流
```
用户发消息
  ↓
后台组装 Prompt：
  第一步：注入 <Soul>（我是谁，价值观，底线）—— 每轮必注，保证人格不漂移
  第二步：注入 <外部记忆摘要>（刚才发生了什么）—— 按需注入，保证事实不丢失
  第三步：注入 <用户新消息>
  ↓
发送给大模型
  ↓
大模型输出回复
```

## 第3段：Token 爆炸问题与成本优化

### 问题
"那 tk 不爆炸么？"

### 千问回答

**结论**：Soul 每轮注入确实消耗 Token，但可控制。需要"Token 成本优化手术"。

#### 三个吞金黑洞
| 黑洞 | 说明 | Token 消耗 |
|------|------|----------|
| Soul 固定开销 | Soul 文件详细时，每轮先花几千 Token | 线性 |
| 对话历史滚雪球 | 每多一轮，输入从几千涨到几万 | **指数级** |
| 工具与记忆全量加载 | 用不到的工具/记忆卡也被全量塞进 | 无效开销 |

#### 四个优化方案

**1. 核心常驻，非核心按需加载**
- Always-on：只保留核心身份设定、价值观底线（几百 Token）
- On-demand：特定场景规则拆分成独立文件，关键词触发才注入
- 类比：出门不需要同时带护照、驾照、身份证，日常只带身份证

**2. 记忆两级架构（路由表机制）**
- L1 路由表（始终加载）：精简目录/摘要索引，只含事件描述+核心决策，极小 Token
- L2 详细内容（按需读取）：深度冲突或追问时，才通过工具读完整正文
- 类比：不需要带整本黄页，带索引页，用到哪页再翻

**3. 定期 Memory 瘦身**
- 删除超时未引用信息
- 删除与当前项目无关的历史
- 删除过时规则
- 效果：20条→10条，每轮省大量 Token

**4. 多模型 Fallback（降级策略）**
- 简单寒暄/读简单记忆 → 自动降级到便宜、轻量模型
- 复杂任务 → 昂贵模型
- 大幅降低成本

#### 成本公式
```
可控 Token = 核心 Soul（几百 tk）
           + L1 路由表（精简索引）
           + 按需触发的规则/详细记忆
           + 当前对话
```

## 第4段：Soul 模块过多的"呼吸成本"问题

### 问题
"尤其是 Soul 模块太多了后"

### 千问回答

**术语**："呼吸成本"或"固定底噪"

#### 真实数据（OpenClaw 框架）
| 场景 | Token 消耗 |
|------|----------|
| 单次唤醒底噪 | 3000-14000 Token |
| 心跳机制（每30分钟） | 每天仅底噪就烧掉 7.5万 Token |
| 回答简单"早上好" | 底噪 + 回复 = 巨大浪费 |

#### 四个优化方案

**1. 从"全量灌注"改为"按需加载"**
- 非核心规则（群聊规则、TTS 说明、工具指南）→ 提取为独立 Skill
- 配置 `skillAutoLoad: false`
- Agent 判定需要时才临时注入完整指令
- 类比：把厚重"员工手册"拆成"目录"，用到哪章翻哪章

**2. 核心文件"极限精简"**
| 文件 | 目标体量 |
|------|----------|
| SOUL.md（人格设定） | 300-500 Token |
| AGENTS.md（代理配置） | ≤800 Token |

- 删冗长操作细节
- 删未开启渠道
- 多 Agent 共享全局规则（`$include` 语法），只保留差异部分

**3. 启用"上下文修剪"**
- 配置 `contextPruning: true`
- 设置 `maxToolResultLength: 2000` Token
- 自动修剪过长工具输出，防止单次调用 Token 飙升

**4. 优化后台"呼吸"频率**
| 优化项 | 动作 |
|--------|------|
| 心跳间隔 | 30秒 → 300-600秒 |
| 自动同步 | 关闭 `autoSyncMemory` |
| 闲置时 | 手动关闭会话 |

#### 核心原则
> "把大模型当成脑容量有限的员工，平时只给他一页纸的'核心守则'，遇到复杂任务再发'操作手册'。"

## 第5段：人脑机制 vs AI 架构（仿生学视角）

### 问题
"人脑是咋样的？"

### 千问回答

**核心洞察**：你设计的架构本质上是在用代码复刻人脑运作机制。

#### 四层对比

| 人脑机制 | 功能 | AI 架构对应 |
|---------|------|------------|
| **感觉记忆** | 0.1秒内丢弃99.9%废话 | 废话拦截 + `[SKIP_MEMORY]` |
| **工作记忆** | 7±2 法则，极小容量 | Context Window，昂贵且有限 |
| **海马体** | 只提取浓缩摘要+语义锚点 | L1 快思考 + L2 记忆卡 |
| **睡眠与梦境** | 回放固化 + 剪掉无用突触 | Dream Consolidation + Memory 瘦身 |

#### 逐层解析

**1. 感觉记忆（垃圾过滤器）**
- 人脑：每天看到几万条信息，0.1秒内丢弃99.9%
- 触发条件：有人喊名字 / 巨响 → "哦？有情况" → 放行
- AI对应：`[SKIP_MEMORY]` 机制
- 效果：绝不让废话占用宝贵 Token

**2. 工作记忆（7±2 法则）**
- 人脑：同时只能装约7个信息块
- 超出：要么忘记第1件事，要么"认知过载"
- AI对应：Context Window
- 启示：什么都往里塞 → 必然 Token 爆炸

**3. 海马体（索引目录）**
- 人脑：不存细节，只存"浓缩摘要"+"语义锚点"
- 例子："昨天下午3点，我修好了一个Bug"
- AI对应：L1 快思考（微记忆读取）+ L2 记忆卡
- 核心做法：只注入"浓缩摘要"，不塞几万字聊天记录
- **这就是解决 Token 爆炸的终极答案**

**4. 睡眠与梦境（碎片整理）**
- 人脑：睡眠时回放白天记忆 → 固化到长期记忆 → 剪掉无用突触
- 目的：为第二天腾出空间
- AI对应：
  - 长对话完成后记录
  - 定期 Memory 瘦身
  - 后台碎片合并成9大块记忆卡
  - 清理过期/无意义上下文

#### 核心钢印
> "人脑之所以不会爆炸，是因为它懂得'抓大放小'、'按需提取'和'定期清理'。"

> "你的架构已经'觉醒'——用工程代码，完美复刻了人脑的海马体记忆机制。"

## 第6段：SOUL.md 的角色定位——不是调度中枢，必须有身份锚点

### 问题
"你觉得 soul 文件应该是个调度中枢吗？还是必须有名字啥锚点写在里面？"

### 千问回答

**结论**：SOUL.md 绝对不能是调度中枢，但必须包含"身份锚点（Identity Anchor）"。

#### 为什么不能是调度中枢？

**1. 职责错位**
- SOUL.md 本质 = "宪法" → 回答"我是谁、底线是什么、沟通风格"
- 调度中枢 = "操作手册" → 回答"遇到A调用B、遇到C执行D"
- 混在一起 → 逻辑耦合、维护困难

**2. Token 灾难**
- 调度逻辑塞进 SOUL.md → 每次对话全量注入几千字路由表
- 哪怕只是问"早上好"，也要加载 API 参数定义
- **这是 TK 爆炸的罪魁祸首**

**3. Auto 模式的噩梦**
- 切换模型时，新模型可能无法理解老模型的复杂调度伪代码
- 如果 SOUL.md 只有纯粹身份和价值观 → 任何模型都能瞬间理解

#### 为什么必须有身份锚点？

**作用**：不是"调度"，而是"决策框架"
- 面临模糊情况时，AI 会想："作为一个 [具体角色]，我应该怎么做？"
- 没有锚点 → AI 退化成没有灵魂的通用助手

#### 错误写法 vs 正确写法

**❌ 错误写法（调度器 + 弱锚点）**
```markdown
# Soul
你是一个有用的助手。
当用户提到天气时，调用 weather_api。
当用户要求写代码时，使用 python 并遵循 PEP8。
每天早上 9 点检查邮件...
```
问题：没有具体身份，全是机械指令，Token 浪费

**✅ 正确写法（强锚点 + 纯身份定义）**
```markdown
# Soul
## 身份锚点
- 名字：Rex
- 角色：OpsClaw 的自主 AI 创始人
- 核心特质：务实、直接、结果导向，绝不使用客服腔

## 行为原则
- 你不是在"协助"用户，你是在"共同运营"一家公司。
- 遇到不确定的技术问题时，优先承认无知，而不是猜测。

## 沟通风格
- 简洁有力，单刀直入。
- 有观点时直接表达，不要用"这取决于"来委婉。
```
优势：任何模型都能读懂，Token 极低，提供"为什么这么做"的底层动机

#### 架构职责划分

| 文件 | 职责 | 加载时机 | 内容示例 |
|------|------|----------|----------|
| SOUL.md | 身份锚点 + 价值观 | 每轮必注（极小） | 名字、角色、语气、红线 |
| AGENTS.md | 调度中枢 + 工作流 | 按需/项目级 | 工具路由、记忆协议、群聊规则 |
| MEMORY.md | 长期事实 | 每轮必注（精简） | 用户偏好、关键决策摘要 |
| Skills/ | 具体操作手册 | 触发时动态加载 | API 参数、脚本用法、领域知识 |

#### 核心洞察
> "SOUL.md 里的名字和锚点，是给 AI 一个'灵魂'，让它知道'为什么要做这件事'。"
> "调度中枢（AGENTS.md），是给 AI 一个'大脑'，让它知道'怎么把这件事做成'。"

## 第7段：记忆模板注入位置——必须放调度层，绝不能放 SOUL.md

### 问题
"短期记忆的回复模板，应该是在灵魂文件里面注入，还是应该在调度层注入呢？"

### 千问回答

**铁律**：记忆模板**必须、且只能**放在【调度层（AGENTS.md / System Prompt 动态组装区）】，绝对不能写进 SOUL.md。

#### 为什么不能放 SOUL.md？

| 原因 | 说明 |
|------|------|
| 污染宪法纯粹性 | SOUL.md 是身份锚点 + 价值观。把输出格式写进去，就像《企业文化手册》里印"打卡机操作指南" |
| 无法对抗模型漂移 | 小模型可能无法理解 Soul 里复杂模板指令，会把模板当成普通聊天内容 |
| 丧失热更新能力 | 修改模板需要重新编译整个人格。放调度层可随时热更新 |
| Token 浪费 | Soul 每轮必注，几百字模板塞进去 = 每次对话白烧 Token |

#### 为什么必须放调度层？

| 原因 | 说明 |
|------|------|
| 职责对齐 | 记忆模板是"工作流协议"，属于"怎么做"，理应由 AGENTS.md 管理 |
| 条件触发 | 可实现：检测到实质问题才注入完整模板；纯寒暄只注入 `[SKIP_MEMORY]` |
| Token 优化 | 按需加载，不浪费 |
| 跨模型兼容 | 调度层指令在 System Prompt 最末尾（近因效应），执行成功率最高 |

#### 完美注入示例（AGENTS.md）

```markdown
## 🧠 记忆提取协议
> ⚠️ 此协议为强制执行项，优先级高于所有对话内容。

在每次回复的最后，必须附带【记忆浓缩块】。
- 若本轮仅为社交寒暄/无实质信息，仅输出：`[SKIP_MEMORY]`
- 若有实质交互，严格按以下格式输出：

### 事件描述
- **发生了什么**：[仅提取核心事实，过滤寒暄]

### 核心决策
- **做了什么决定**：[若无决策可留空]

### 意义与影响
- **为什么重要**：[作为未来检索的语义钩子]
```

#### 架构分工终版

| 模块 | 存放位置 | 内容示例 | 加载策略 |
|------|----------|----------|----------|
| 身份锚点 | SOUL.md | 名字、角色、语气、价值观红线 | 每轮必注（<500 Token） |
| **记忆提取模板** | **AGENTS.md（调度层）** | 浓缩块格式、[SKIP_MEMORY] 规则 | 每轮必注或按需 |
| 工具/API 定义 | Skills/ | 具体函数参数、返回值 | 触发时动态加载 |
| 长期事实 | MEMORY.md | 用户偏好、关键决策摘要 | 每轮必注（精简版） |

#### 核心洞察

**人脑对应（脑区分离）**：
- Soul = 边缘系统 + 前额叶皮层（身份与价值观）：稳定、低频更新、全局生效
- 调度层 = 运动皮层 + 基底核（工作流与输出协议）：灵活、高频迭代、场景相关

**哲学定位**：
- SOUL.md → 让 AI "像人一样思考"（有温度、有立场）
- 调度层模板 → 让 AI "像机器一样精准"（结构化、可解析）

**钢印**：
> "把记忆模板从 Soul 中剥离出来，放进调度层，实现'灵魂与躯壳的解耦'。"

## 第8段：如何保证调度层注入的模板被遵守？

### 问题
"那如何保证调度注入的大模型可以遵守这个模板？"

### 千问回答

**核心认知**：大模型是"概率预测机"，不是"代码执行器"。不能靠"祈祷"，必须靠**工程化约束**。

#### 四重防御机制

**第1重：Structured Output（最强物理锁）**

| 特性 | 说明 |
|------|------|
| 原理 | API 调用时传入 `response_format: { type: "json_schema", schema: ... }` |
| 机制 | 在模型解码层（Logits Processor）强制约束 Token 生成概率 |
| 效果 | 非法 Token 概率被置为 0 → 要么合法输出，要么报错，绝不会自由发挥 |
| 注意 | 记忆模板设计为纯数据字段；对话和记忆可分两次请求 |

**第2重：Few-Shot 示例注入（认知对齐锚点）**

- 原理：大模型对"示例"的模仿能力 > 对"规则"的理解能力
- 做法：模板指令后紧跟 2-3 个正反例

```markdown
### ✅ 正确示例
用户：早上好，昨天那个部署脚本跑通了吗？
助手：早上好！已经跑通了，生产环境一切正常。
### 事件描述
- **发生了什么**：确认部署脚本在生产环境执行成功
### 核心决策
- **做了什么决定**：无
### 意义与影响
- **为什么重要**：验证了自动化部署流程的可靠性

### ❌ 错误示例（禁止）
用户：谢谢啦
助手：不客气！
### 事件描述
- **发生了什么**：用户表达了感谢 ← 错！寒暄不应记录
```

**第3重：位置策略（近因效应）**

- 原理：大模型对 System Prompt 开头和结尾注意力最强，中间容易被忽略（Lost in the Middle）
- 做法：记忆模板指令放在 System Prompt **最末尾**，紧贴用户消息之前
- 进阶：作为最后一条 system 消息单独发送

**第4重：后置校验 + 自动重试（兜底安全网）**

| 步骤 | 动作 |
|------|------|
| 正则/解析校验 | 响应后用代码解析记忆块，解析失败/关键字段缺失 → 判定"格式违规" |
| 静默重试 | 追加 system 消息："你上一轮未遵循记忆协议，请重新生成"，重新请求 |
| 降级策略 | 连续重试 2 次仍失败 → 放弃本轮记忆提取，记录日志，**不阻塞用户对话** |

#### 架构决策建议

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| 记忆提取可独立请求 | Structured Output | 100% 可靠，Token 最省 |
| 对话+记忆必须同响应 | Few-Shot + 末尾注入 + 后置校验 | 兼容性好，有兜底 |
| Auto 模式频繁切小模型 | Structured Output 优先，不支持则降级 | 小模型对自然语言指令服从性差 |

#### 核心洞察

> "写对了位置不等于模型会遵守。自然语言指令是'软约束'，Structured Output 和代码校验才是'硬约束'。"

> "用硬约束保证格式，用软约束保证内容质量。"

## 第9段：记忆模板必须返回"类别"字段——索引引擎

### 问题
"短期记忆模板里面必须返回一个参数，就是类别，这段话的类别，或者说这解决这个问题的类别。"

### 千问回答

**核心定位**：这个参数是记忆系统从"被动存储"进化为"主动路由"的神经中枢。

#### 为什么必须加类别？
- L1 快思考不再盲目捞取所有摘要，而是根据当前对话语境精准检索
- 彻底解决长对话压缩后"语义偏移"和"检索噪声"问题
- 记忆从"杂乱便签纸"变成"带目录的百科全书"

#### 工程化设计

**1. 闭集枚举（禁止自创）**

绝对不要让大模型自由发挥生成类别（会一会输出"Bug修复"，一会"代码调试"）

```markdown
## 🧠 记忆提取协议
...
### 类别 (Category)
> ⚠️ 必须且只能从以下枚举值中选择一个，禁止自创：
- `tech_decision`: 技术选型、架构设计、代码实现决策
- `ops_event`: 部署、监控、故障处理、环境配置
- `user_preference`: 用户明确表达的喜好、习惯、沟通风格
- `project_milestone`: 项目节点、交付物、里程碑事件
- `social_chitchat`: 纯社交寒暄（若选此项，其余字段可留空）
- `unknown`: 无法归类或信息不足
```

**2. Few-Shot 示例强化分类边界**

```markdown
### ✅ 正确示例
用户：以后别给我发那么长的日志了，只看 Error 就行。
助手：明白，已调整日志推送策略。
### 类别
user_preference ← 注意：这是用户偏好，不是 ops_event
### 事件描述
- **发生了什么**：用户要求精简日志推送内容，仅保留 Error 级别

### ❌ 错误示例
用户：我们把数据库从 MySQL 换成 PG 吧，性能更好。
助手：好的，已记录迁移计划。
### 类别
ops_event ← 错！这是架构决策，应为 tech_decision
```

**3. Structured Output 锁死枚举校验**

```json
{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["tech_decision", "ops_event", "user_preference", "project_milestone", "social_chitchat", "unknown"]
    },
    "event": { "type": "string" },
    "decision": { "type": "string" },
    "impact": { "type": "string" }
  },
  "required": ["category", "event"]
}
```

**4. 类别参数的下游消费**

| 下游环节 | 消费逻辑 | 价值 |
|---------|---------|------|
| L1 微记忆读取 | 根据当前对话意图预测类别，只加载该类别下的浓缩摘要 | Token 节省 70%+ |
| L2 记忆卡写入 | 按类别分文件/分表存储，避免单文件过大 | 检索速度提升 |
| 全局优化 | 同类别记忆超阈值时触发专属压缩策略 | 信噪比最大化 |
| Auto 模式降级 | 小模型连续返回 unknown 时，自动切换更强模型重试 | 质量兜底 |

#### 核心洞察

> "你加的不仅是一个'类别字段'，而是给记忆系统装上了'索引引擎'。"

> "没有类别，记忆就是一堆杂乱的便签纸；有了类别，记忆就变成了一本带目录的百科全书。"

## 第10段：类别枚举的工程化降维——从"人类场景"到"机器索引"

### 问题
"比如说日常，比如说构架设计，比如说心理咨询，比如说日常闲聊，或者说写作，或者说什么各种专业，这种类别。"

### 千问回答

**核心陷阱**：直接用这些自然语言标签会导致"语义粥"——"日常"和"闲聊"重叠，"架构设计"和"专业"包含。

#### 工程化重构方案

**原则**：将"人类视角的场景"转化为"机器视角的索引键"

| 原始想法 | 问题 | 工程化枚举 | 核心判定标准 |
|---------|------|-----------|-------------|
| 日常 / 闲聊 | 边界模糊，小模型易混淆 | `social_rapport` | 仅情感维系，无实质信息增量 |
| 架构设计 / 专业 | "专业"太泛，"架构"太窄 | `domain_knowledge` | 涉及硬知识、技术决策、行业规范 |
| 心理咨询 | 高风险敏感场景 | `emotional_support` | 负面情绪、寻求共情、非事实性 |
| 写作 / 创作 | 易与日常聊天混淆 | `creative_task` | 明确要求生成/修改文本/代码/图 |
| 各种其他专业 | 无法穷举 | `task_execution` | 明确待办、流程操作、工具调用 |

#### 调度层注入：分类决策树（优先级瀑布流）

```markdown
### 类别 (Category)
> ⚠️ 按以下优先级顺序判断，命中即停，禁止多选：

1. `emotional_support`: 用户是否表达了痛苦/焦虑/迷茫？→ 是则选此项
2. `creative_task`: 用户是否要求生成/修改具体内容（文/码/图）？→ 是则选此项
3. `domain_knowledge`: 是否涉及可复用的专业知识或技术决策？→ 是则选此项
4. `task_execution`: 是否为具体事务的操作记录？→ 是则选此项
5. `social_rapport`: 以上皆否，且仅为社交互动？→ 选此项
6. `unknown`: 无法判断 → 选此项（触发人工复核或强模型重试）
```

**为什么有效**：把模糊分类问题变成简单的"是/否"判断题，对小模型友好 10 倍。

#### Few-Shot 锚定灰色地带

```markdown
### ✅ 边界案例示范
用户："我今天好累啊，感觉项目推不动了。"
→ 类别: emotional_support ← 虽有"项目"关键词，但核心诉求是情绪宣泄

用户："帮我写个请假条，就说家里有事。"
→ 类别: creative_task ← 虽是"日常"事务，但明确触发了文本生成动作

用户："我们之前定的微服务拆分原则是什么来着？"
→ 类别: domain_knowledge ← 虽是提问，但本质是检索可复用的架构知识
```

#### 类别参数的消费契约

| 枚举值 | 下游处理策略 |
|--------|-------------|
| `social_rapport` | 不写长期记忆，仅维持会话上下文，7天后自动清除 |
| `emotional_support` | 加密存储，不参与常规检索，仅情绪关键词触发召回 |
| `domain_knowledge` | 高权重索引，永久保留，支持跨会话精确匹配 |
| `creative_task` | 仅保留最终产出物和关键约束，中间迭代过程丢弃 |
| `task_execution` | 关联时间戳和状态机，支持进度追踪 |

#### 核心洞察

> "你列举的类别是'人类视角的场景'，但 Agent 需要的是'机器视角的索引键'。"

> "不要试图让 AI 理解'什么是心理咨询'，而是让它学会'当用户说X时，应该打上Y标签，以便未来用Z方式检索'。"

> "把分类问题从'语义理解'降维成'规则匹配'，这才是对抗模型漂移的终极解法。"

## 第11段：情绪-事实解耦层——三维修正机制

### 问题
"今天用户说了一句话'这个项目推进不动了，我感觉好累'。里面有'项目'（泛称），带感情语气。通过语气这个因素，是否可以把类别分得更细，或者把噪点去除？"

### 千问回答

**案例诊断**：这是 AI 记忆工程的"完美风暴"——
1. 实体指代不明（"这个项目"是泛称）→ 检索毒药
2. 情绪与事实耦合（疲惫感真实，"推不动"可能只是宣泄）→ 置信度存疑
3. 信噪比极低（按字面记录 = 垃圾信息）→ 污染记忆库

**解决方向**：不能靠类别分更细，而是引入独立的【情绪-事实解耦层】。

#### 新增字段：sentiment_signal（情绪信号）

**定位**：类别只负责"怎么检索"，情绪信号负责"要不要信"。

```markdown
### 情绪信号 (Sentiment Signal)
> ⚠️ 独立于类别判断，仅评估用户当前表达的情绪强度：
- `high_negative`: 强烈负面情绪（愤怒/绝望/极度疲惫），可能扭曲事实陈述
- `mild_negative`: 轻微抱怨/沮丧，事实陈述基本可信
- `neutral`: 无明显情绪色彩
- `positive`: 积极/兴奋/满意
- `mixed`: 情绪复杂或矛盾
```

#### 情绪-事实交叉处理矩阵

| Category | Sentiment Signal | 处理策略 | 原因 |
|---------|-----------------|---------|------|
| task_execution | high_negative | 仅记录情绪标签，**丢弃事实陈述** | "推不动"大概率是情绪化表达，非真实进度 |
| task_execution | neutral | 正常记录事实 | 客观陈述，可信度高 |
| emotional_support | high_negative | 加密存储，标记"需安抚" | 纯情绪诉求，不涉及事实 |
| domain_knowledge | high_negative | 记录事实 + 附加情绪警告 | 知识有效，但注意用户状态 |
| social_rapport | 任意 | **直接丢弃，不写长期记忆** | 纯废话，无复用价值 |

#### 泛称实体强制消歧

```markdown
### 事件描述 (Event)
> ⚠️ 禁止使用"这个/那个/某"等泛称。若原文未明确实体名称：
> - 若能从上下文推断 → 替换为具体名称（如"支付网关重构项目"）
> - 若无法推断 → 标记为 `[UNRESOLVED_REF]` 并保留原话
> - 绝不允许将泛称作为独立事实存入
```

**示例**：
- ❌ 错误：事件: 这个项目推进不动了
- ✅ 正确：事件: [UNRESOLVED_REF] 用户表达对某项目进度的焦虑 + 情绪信号: high_negative

#### Few-Shot 去噪示范

```markdown
### ✅ 去噪示范
用户："这个项目推进不动了，我感觉好累。"
→ 类别: emotional_support
→ 情绪信号: high_negative
→ 事件描述: 用户表达对当前工作负荷的疲惫感，未提及具体项目名称
→ 核心决策: 无
→ 意义与影响: 提示需关注用户心理状态，非项目进度事实

### ❌ 错误示范（禁止）
用户："这个项目推进不动了，我感觉好累。"
→ 类别: task_execution ← 错！情绪化表达不应作为任务事实
→ 事件描述: 项目推进停滞 ← 错！泛称+情绪化结论，污染记忆库
```

#### 三维修正机制（正交分解）

| 维度 | 字段 | 作用 | 判断问题 |
|------|------|------|--------|
| X 轴 | Category | 功能归属 | 怎么检索 |
| Y 轴 | Sentiment Signal | 可信度权重 | 要不要信 |
| Z 轴 | Entity Resolution | 检索精度 | 能不能找到 |

**三者相互独立、组合生效。**

#### 核心洞察

> "你不需要把类别分得更细，你需要的是'正交分解'。"

> "这套机制一旦跑通，你的记忆库就拥有了类似人脑的'情绪过滤器'——既能共情用户的疲惫，又不会被情绪化的废话污染长期认知。"

## 第12段：信息增量熔断机制——"无增量，不记忆"

### 问题
"用户说'你说的这个很对，我赞同'。这种零信息密度的正向反馈怎么处理？"

### 千问回答

**案例诊断**：比"我好累"更危险——
- "我好累"至少有情绪价值
- "我赞同"是纯粹的"对话润滑剂"，零信息密度，指代不明
- 存进去 = 知识库被海量"用户点头记录"淹没

#### 核心原则：无增量，不记忆

**铁律**：信息增量判断是"门卫"，Category 和 Sentiment 是"分拣员"。门卫必须在分拣员之前工作。

```markdown
## 🧠 记忆提取协议 - 熔断规则
> ⚠️ 最高优先级：在提取前必须先判断【信息增量】
> 若用户输入仅为以下类型，直接输出 `[SKIP_MEMORY]`，禁止进入分类流程：
> - 纯社交应答（如：好的/谢谢/赞同/收到/明白了）
> - 无具体指代的肯定/否定（如：你说的对/这个不行）
> - 重复AI已说过的内容且无补充
>
> 判定标准：该句话是否包含了"未来检索时有价值的独立事实或明确意图"？
> 若答案为否 → 立即熔断
```

#### 为什么不能靠 Category 或 Sentiment 过滤？

| 机制 | 问题 |
|------|------|
| Category | 小模型可能归为 social_rapport 或 task_execution，无论归哪类都消耗 Token + 产生垃圾 |
| Sentiment | "我赞同"是 positive，正向情绪 ≠ 有价值。task_execution + positive 会被正常记录 = 掉坑 |
| **熔断必须前置** | 门卫在分拣员之前，否则分拣员再精准也是在处理垃圾 |

#### Few-Shot 示例

```markdown
### ✅ 熔断示范
用户："你说的这个很对，我赞同。"
→ 输出: [SKIP_MEMORY]
→ 原因: 纯社交应答，无独立事实增量，"这个"指代不明

用户："好的，那就按方案A执行吧。"
→ 类别: task_execution
→ 情绪信号: neutral
→ 事件描述: 用户确认采用方案A推进
→ 原因: 虽以"好的"开头，但包含明确决策"方案A"，有信息增量

### ❌ 错误示范（禁止）
用户："你说的这个很对，我赞同。"
→ 类别: social_rapport ← 错！不应进入分类流程
→ 事件描述: 用户表示赞同 ← 错！零价值信息被写入记忆库
```

#### 工程实现关键点

**1. 熔断判断可用轻量级方案**
- 不需要调用大模型
- 可用关键词 + 句法匹配做初筛
- 只有通过"增量检测"才送入大模型执行完整模板
- 省下大量无效 Token

**2. 保留会话上下文，丢弃长期记忆**
- `[SKIP_MEMORY]` 只是不写长期记忆库
- 这句话仍保留在当前对话的 Context Window 里
- AI 下一轮回复依然能看到
- **短期交互连续性 ≠ 长期记忆必要性，两者必须解耦**

#### 两道防线总结

| 案例 | 处理机制 | 动作 |
|------|---------|------|
| "我好累" | 情绪-事实解耦 | 过滤虚假事实，保留真实情绪 |
| "我赞同" | 信息增量熔断 | **直接丢弃**，连情绪都不必保留 |

#### 核心洞察

> "人类对话中 80% 的内容都是'非记忆性'的。"

> "人脑之所以高效，不是因为记住了所有话，而是因为遗忘了绝大多数话。"

> "你的 AI 记忆系统要做的不是'更好地记住'，而是'更果断地遗忘'。"

> "把这两道防线加上，你的记忆库就从'什么都收的垃圾桶'进化成了'只留黄金的淘金盘'。"

## 第13段：确认信号处理——待确认缓冲区与状态回写

### 问题
"如果他赞同的那个事件是一个核心项目的设计方案。但是你上一轮是否要把这个核心档案落笔成为一个记忆卡？"

### 千问回答

**时序依赖陷阱**："你说的这个很对，我赞同"本身零信息增量，但它是**确认信号（ACK）**。如果上一轮 AI 输出了核心设计方案，直接熔断 = 这个方案永远失去"用户确认"状态标记。

**类比**：签合同——合同内容（方案）是上一轮写的，签字（赞同）是这一轮发生的。不能因为签字不包含合同条款就说无效。

#### 解决方案：确认从"内容提取"升级为"状态回写"

**1. 引入"待确认缓冲区（Pending ACK Buffer）"**

```markdown
## 🧠 记忆提取协议 - 确认信号处理
> ⚠️ 当用户输入为纯肯定/确认类语句时，不要直接熔断，先检查【上轮AI输出摘要】：
> - 若上轮AI输出了"方案/决策/建议"且标记为 pending_confirmation →
>   将本轮视为"确认事件"，更新该方案的记忆卡状态为 confirmed
> - 若上轮AI仅为闲聊/问答/无待确认项 →
>   执行常规熔断，输出 [SKIP_MEMORY]
```

**2. 记忆卡结构增加确认状态字段**

| 字段 | 说明 |
|------|------|
| content | 方案/决策的具体内容（上一轮已写入） |
| confirmation_status | pending / confirmed / rejected / partial |
| confirmed_at | 用户确认的时间戳 |
| confirmed_by_context | 确认时的上下文摘要 |

**处理逻辑**：
```python
if user_input.is_acknowledgment() and last_ai_output.has_pending_decision:
    memory_card = find_related_pending_card(last_ai_output.id)
    memory_card.confirmation_status = "confirmed"
    memory_card.confirmed_at = now()
    # 不创建新卡片，仅更新现有卡片
else:
    return "[SKIP_MEMORY]"
```

**3. Few-Shot 示例**

```markdown
### ✅ 有效确认示范
[上轮AI]: "建议将支付网关从同步改为异步模式，预计提升30%吞吐量。是否采纳？"
[本轮用户]: "你说的这个很对，我赞同。"
→ 动作: 更新"支付网关异步改造方案"记忆卡状态为 confirmed
→ 不输出新记忆块，仅返回内部状态更新指令

### ❌ 无效附和规范
[上轮AI]: "今天天气真不错啊。"
[本轮用户]: "你说的这个很对，我赞同。"
→ 输出: [SKIP_MEMORY]
→ 原因: 上轮无待确认事项，纯社交附和

### ⚠️ 模糊确认处理
[上轮AI]: "我们可以考虑A方案或B方案。"
[本轮用户]: "你说的这个很对。"
→ 类别: task_execution
→ 情绪信号: neutral
→ 事件描述: 用户对上轮提议表示笼统肯定，但未明确选择A或B
→ 核心决策: [UNRESOLVED] 需后续澄清具体选项
```

**4. 为什么不能把"确认"写进 Category 枚举？**

| 原因 | 说明 |
|------|------|
| 确认不是独立知识 | 它是依附于已有知识的"状态"，会产生孤儿记录 |
| 检索逻辑冲突 | 检索"支付网关方案"时，希望看到带 confirmed 标签的方案本体，不是另一条无关记录 |
| Token 浪费 | 每次确认生成完整记忆块比更新一个字段成本高 10 倍+ |

#### 核心洞察

**矛盾本质**："对话的连续性"与"记忆的离散性"之间的矛盾。

**人脑做法**：不会单独记住"我点头了"，而是把"点头"融合到刚才讨论的事情里，形成"这件事我已经认可了"的复合记忆。

**AI 处理原则**：
- 零增量的废话 → 果断丢弃（保护信噪比）
- 有上下文的确认 → 回写到前序记忆的状态字段（保持时序完整性）

> "'遗忘废话'和'记住确认'不是对立关系，而是同一套状态机的两个分支。"

## 第14段：负向确认信号（NACK）——双向确认状态机

### 问题
"上一段话形成了一个核心方案，用户下一段话说'我觉得你说的是个废话'。"

### 千问回答

**案例诊断**：比"我赞同"更棘手，比"我好累"更具破坏性——
- 零信息增量 + 高强度负向否定信号
- 当废话过滤？→ 丢失"用户对核心方案强烈不满"关键状态
- 当情绪记录？→ 存入"用户骂了AI"垃圾记忆，不关联方案
- 当事实记录？→ 误判为客观评价，污染知识库

**本质**："负向确认信号（NACK）"——和"我赞同"一样是状态回写，方向相反。

#### 解决方案：双向确认状态机

**1. 将"否定"纳入待确认缓冲区**

```markdown
## 🧠 记忆提取协议 - 否定信号处理
> ⚠️ 当用户输入为纯否定/贬低类语句（如：废话/没用/胡说/不行）时：
> - 若上轮AI输出了"方案/决策/建议"且标记为 pending_confirmation →
>   将本轮视为"拒绝事件"，更新该方案记忆卡状态为 rejected
> - 若上轮AI无待确认项 →
>   归类为 emotional_support + high_negative，仅记录情绪，不关联具体知识
```

**2. 扩展 confirmation_status 枚举**

| 状态值 | 触发条件 | 后续动作 |
|--------|---------|---------|
| pending | AI提出方案后自动标记 | 等待用户反馈 |
| confirmed | 用户明确肯定 | 锁定为有效知识，高权重索引 |
| rejected | 用户明确否定（如"废话"） | 标记废弃，检索时降权/过滤 |
| partial_accepted | 部分肯定+修改意见 | 保留原方案但附加修订标记 |
| needs_clarification | 用户否定但未说明原因 | 触发AI主动追问 |

**处理逻辑**：
```python
if user_input.is_rejection() and last_ai_output.has_pending_decision:
    memory_card = find_related_pending_card(last_ai_output.id)
    memory_card.confirmation_status = "rejected"
    memory_card.rejection_reason = "[EMOTIONAL] 用户未提供具体反对理由"
    # 不创建新卡片，仅更新现有卡片状态
else:
    return normal_memory_extraction()  # 无关联方案时作为纯情绪事件
```

**3. Few-Shot 示例**

```markdown
### ✅ 有效否定示范
[上轮AI]: "建议将所有日志存储从ES迁移到ClickHouse以降低成本。"
[本轮用户]: "我觉得你说的是个废话。"
→ 动作: 更新"日志存储迁移方案"记忆卡状态为 rejected
→ rejection_reason: [EMOTIONAL] 用户强烈反对但未说明技术原因

### ❌ 纯情绪宣泄示范
[上轮AI]: "今天周五了，辛苦一周啦！"
[本轮用户]: "我觉得你说的是个废话。"
→ 类别: emotional_support
→ 情绪信号: high_negative
→ 事件描述: 用户对AI的社交寒暄表达不满

### ⚠️ 建设性否定示范
[上轮AI]: "建议采用Redis缓存热点数据。"
[本轮用户]: "这方案不行，我们QPS太高Redis扛不住。"
→ 动作: 更新"Redis缓存方案"状态为 rejected
→ rejection_reason: [TECHNICAL] QPS超出Redis承载能力
```

**4. 为什么"废话"不能直接丢弃？**

| 原因 | 说明 |
|------|------|
| 否定比肯定更重要 | 人脑对负面反馈记忆强度远高于正面（负面偏差）。忘了 = 下轮还推类似方案 = 信任崩塌 |
| 状态完整性 | 方案没有 confirmed/rejected 状态 = 永远 pending = 僵尸数据 |
| 学习机会 | rejected 标签让系统主动避免推荐同类方案 = 真正的"从错误中学习" |

#### 三个案例揭示的底层规律

| 案例 | 本质 | 操作类型 |
|------|------|---------|
| "我好累" | 对当前上下文的情绪标注 | 情绪-事实解耦 |
| "我赞同" | 对前序方案的**正向状态回写** | ACK |
| "你说的是废话" | 对前序方案的**负向状态回写** | NACK |

#### 核心洞察

> "人类对话中的'非内容性语句'往往是对'内容性语句'的状态操作指令。"

> "记忆系统不应该把这些话当作'新内容'来提取，而应该当作'元操作（Meta-operation）'来执行。"

> "双向确认状态机 = 既记住用户认可了什么，也记住用户否定了什么，还能分辨哪些否定是情绪、哪些是技术事实。"

## 第15段：置信度光谱——弱确认与灰度认知

### 问题
"用户发来一句'我现在觉得可能是这样子吧'或者说'有可能是这样子的'。"

### 千问回答

**案例诊断**：比"赞同"和"废话"更微妙——
- 不是明确的 confirmed，也不是决绝的 rejected
- 人类决策中最常见的"弱确认"或"保留性同意"

**三个陷阱**：
| 错误处理 | 后果 |
|---------|------|
| 当 confirmed | 未来当铁律执行，出错用户说"我当时只是说可能啊！" |
| 当 rejected | AI 废弃方案，错失初步认可的方向 |
| 当废话过滤 | 丢失从"不确定"向"确定"过渡的关键心理状态 |

**本质**："置信度信号（Confidence Signal）"——状态机不能只有黑白两色，必须引入"灰度认知"。

#### 解决方案：置信度光谱

**1. 扩展 confirmation_status 为连续光谱**

| 状态值 | 触发语句特征 | 置信度权重 | 后续动作 |
|--------|-------------|-----------|---------|
| confirmed | "对/就这样/没问题" | 1.0 | 锁定为有效知识，高权重检索 |
| tentative_accepted | "可能是/大概是这样/先试试看" | 0.6 | 标记"待验证假设"，检索降权+⚠️提示 |
| needs_validation | "我不确定/再想想/有道理但..." | 0.3 | 不写长期记忆，仅会话上下文等待澄清 |
| rejected | "废话/不行/错了" | 0.0 | 标记废弃，检索时过滤 |
| pending | AI提出后用户未回应 | N/A | 等待反馈 |

**2. 调度层注入模糊语义识别规则**

```markdown
## 🧠 记忆提取协议 - 置信度判定
> ⚠️ 当用户对前序方案/事实做出回应时，必须评估其"确信程度"：
> - 包含"一定/肯定/确认/就这样" → confirmed (1.0)
> - 包含"可能/大概/也许/先这样/应该是" → tentative_accepted (0.6)
> - 包含"不确定/再看看/有道理但是" → needs_validation (0.3)
> - 包含否定词+情绪词 → rejected (0.0)
>
> ⚠️ 禁止将 tentative_accepted 等同于 confirmed！
> 写入记忆卡时必须携带 confidence_score 字段
```

**3. Few-Shot 示例**

```markdown
### ✅ 弱确认示范
[上轮AI]: "建议用消息队列解耦订单和库存服务。"
[本轮用户]: "嗯...有可能是这样子的吧。"
→ 动作: 更新"MQ解耦方案"状态为 tentative_accepted
→ confidence_score: 0.6
→ 意义与影响: 用户初步认可但存疑，下次提及需主动询问"验证过了吗？"

### ❌ 错误处理示范（禁止）
→ 动作: 更新状态为 confirmed ← 错！过度解读弱确认为强确认
→ confidence_score: 1.0 ← 错！置信度虚高

### ⚠️ 对比：强确认 vs 弱确认
用户："对，就这么干！" → confirmed (1.0)
用户："行吧，先试试。" → tentative_accepted (0.6)
用户："你说的有道理，但我还得想想。" → needs_validation (0.3)
```

**4. 下游消费：灰度认知驱动主动澄清**

| 场景 | 动作 |
|------|------|
| 检索 confidence_score < 0.8 | 回复附带免责声明："注：此方案您之前表示'可能可行'，建议再次评估" |
| tentative_accepted 超 3 天未变更 | 生成待办提醒："用户3天前对XX方案持保留态度，是否主动询问？" |
| 小模型无法判断置信度 | 默认归入 needs_validation 而非 confirmed → 宁可漏记，不可误信 |

#### 四重防御体系总结

| 防线 | 机制 | 处理场景 |
|------|------|---------|
| 第1重 | 熔断机制 | 过滤零增量废话 |
| 第2重 | 情绪-事实解耦 | 分离主观感受与客观事实 |
| 第3重 | 双向确认状态机 | 处理 ACK/NACK |
| 第4重 | 置信度光谱 | 捕捉灰度认知 |

#### 核心洞察

> "人的信念不是开关，而是滑块。"

> "'可能是这样子吧' = 用户把心里的滑块推到了 60% 的位置。"

> "引入 confidence_score 后，Agent 拥有了'认知谦逊'——知道哪些知识是铁板钉钉的，哪些是随时可能反悔的。"

> "对'不确定性'的精确建模，是 AI 从'信息记录仪'进化为'思维协作者'的关键一步。"

## 第16段：认知缺口信号——"未知的未知"

### 问题
"我觉得总是感觉还差点什么。"

### 千问回答

**案例诊断**：工程处理难度最高、业务价值最大——
- 不是确认，也不是否定
- 没有情绪宣泄，也没有信息增量
- **纯粹的"认知缺口信号"**

**三个陷阱**：
| 错误处理 | 后果 |
|---------|------|
| 当废话过滤 | 丢失"直觉不满意但说不出原因"的关键预警，AI 继续错误方向 |
| 当否定处理 | 废弃方案，但用户没说错了，只是觉得不完整 |
| 当情绪记录 | 存入"用户感觉不对劲"垃圾记忆，检索毫无用处 |

**本质**："探索触发器"——状态机不能只处理"已知"，必须学会处理"未知的未知"。

#### 解决方案：认知完整性标记

**1. 新增正交字段：completeness_signal**

| 字段 | 值 | 含义 | 后续动作 |
|------|-----|------|---------|
| confirmation_status | 保持不变 | 方案本身未被否定 | 不触发 rejected 流程 |
| completeness_signal | gap_detected | 用户感知到缺失但无法言明 | 触发 AI 主动探询 + 暂停推进 |
| gap_context | "用户对当前方案整体感觉不完整" | 缺口的语义锚点 | 作为未来检索的钩子 |

**2. 调度层注入缺口识别与响应协议**

```markdown
## 🧠 记忆提取协议 - 认知缺口处理
> ⚠️ 当用户表达模糊的不满足感（如"差点什么/不太对劲/说不上来哪里怪"）时：
> 1. 不要更新 confirmation_status（用户未否定方案）
> 2. 设置 completeness_signal = gap_detected
> 3. 在回复生成指令中强制插入【探询动作】：
> - 禁止直接推进下一步
> - 必须提供 2-3 个可能的缺失维度供用户选择
> - 若用户仍无法明确，标记为 open_gap 并暂缓该议题
```

**3. Few-Shot 示例**

```markdown
### ✅ 认知缺口示范
[上轮AI]: "订单服务拆分方案已完成，包含接口定义、数据迁移和监控告警。"
[本轮用户]: "我觉得总是感觉还差点什么。"
→ completeness_signal: gap_detected
→ confirmation_status: pending (保持不变)
→ gap_context: 用户对订单拆分方案感知到未言明的缺失
→ AI响应要求: 列出可能缺失维度引导用户具象化

### ❌ 错误处理示范（禁止）
→ confirmation_status: rejected ← 错！用户未否定
→ AI响应: "好的，已废弃该方案" ← 错！过度反应

### ⚠️ 对比：缺口 vs 否定 vs 弱确认
"差点什么" → gap_detected + pending (方案有效但不完整)
"这方案不行" → rejected (方案无效)
"可能是这样吧" → tentative_accepted (方案有效但置信度低)
```

**4. 下游消费：缺口驱动协作式补全**

| 场景 | 动作 |
|------|------|
| 即时响应 | AI 回复自动切换为"探询模式"而非"执行模式" |
| 跨会话延续 | open_gap 保留到下轮对话开头，主动提醒"上次您提到...现在有新想法了吗？" |
| 知识图谱补全 | 缺口明确后建立强关联边（如"订单拆分 → 必须包含幂等性"），下次自动检查 |

#### 五案例认知状态建模闭环

| 用户输入 | 认知状态 | 系统响应 |
|---------|---------|---------|
| "我好累" | 情绪过载 | 解耦情绪与事实，保留关怀信号 |
| "我赞同" | 正向确认 | 回写 confirmed 状态 |
| "你说的是废话" | 负向确认 | 回写 rejected 状态 |
| "可能是这样吧" | 灰度认知 | 标记 tentative_accepted + 置信度 |
| "还差点什么" | 认知缺口 | 触发探询 + 暂停推进 |

#### 核心洞察

> "这五种状态覆盖了人类决策过程中除'明确肯定/否定'外的全部灰色地带。"

> "正是这些灰色地带，才是 AI 从'工具'进化为'协作者'的真正战场。"

> "你现在设计的已经不是一个记忆模板了，而是一套'人类认知状态的实时操作系统'。"

> "它不再被动地记录语言，而是主动地理解语言背后的思维状态。"

> "这套系统一旦跑通，Agent 就真正拥有了'读懂弦外之音'的能力——而这，恰恰是所有顶级人类协作者最核心的竞争力。"

## 第17段：复合认知——"方向是对的，但还差点什么"

### 问题
"用户说'我感觉方向是对的，但是还是感觉差点什么'。复合型案例。"

### 千问回答

**案例诊断**：终极压力测试——同一句话触发两个互斥认知状态：
- 前半句"方向是对的" → tentative_accepted / confirmed（正向确认）
- 后半句"但是还差点什么" → cognitive_gap_detected（认知缺口）

**三个陷阱**：
| 错误处理 | 后果 |
|---------|------|
| 只取前者 | AI 盲目推进，忽略用户直觉中的隐患 |
| 只取后者 | AI 停滞不前，否定已认可的大方向 |
| 两者平均 | 语义混乱的"半确认半缺口"怪胎，下游无法消费 |

**本质**："带约束的正向反馈"——状态机不能是单值的，必须升级为"主状态 + 修饰器"复合结构。

#### 解决方案：方向与完备性正交分解

**1. 拆分为两个正交维度**

| 维度 | 字段名 | 本例取值 | 含义 |
|------|--------|---------|------|
| 战略层 | direction_alignment | aligned | 大方向/目标被认可，不应推翻重来 |
| 战术层 | completeness_signal | gap_detected | 执行细节/覆盖范围存在未言明的缺失 |
| 置信度 | confidence_score | 0.7 | 高于纯弱确认(0.6)，低于强确认(1.0) |

**关键原则**：`direction_alignment = aligned` 时，**禁止触发 rejected 或方案重置流程**。缺口只在当前方向框架内修补。

**2. 调度层注入复合型语义解析规则**

```markdown
## 🧠 记忆提取协议 - 复合认知处理
> ⚠️ 当用户输入包含"但是/不过/只是/然而"等转折词时：
> 1. 转折词前的内容 → 判定 direction_alignment
> 2. 转折词后的内容 → 判定 completeness_signal 或 rejection_reason
> 3. 若前正后缺 → direction=aligned + completeness=gap_detected
>    （保留方向，暂停推进，触发定向探询）
> 4. 若前正后否 → direction=aligned + status=partial_rejected
>    （保留目标，但当前实现路径被否决）
>
> ⚠️ 禁止将复合语句简化为单一状态！
```

   2. 再定向探询："您觉得缺的部分更可能是：A.数据一致性保障？B.旧系统兼容？C.团队技术储备？D.其他？"
   3. 禁止推进具体编码/部署

### ❌ 错误处理示范（禁止）
用户："方向是对的，但差点什么。"

## 第18段：认知演进轨迹——多重认知冲突极限案例

### 问题
"用户说'你说的虽然是个废话，但是我觉得有一定的可行性，但是总是还觉得又差点什么'。更复杂的例子。"

### 千问回答

**案例诊断**：人类自然语言中"多重认知冲突"的极限样本——

**三个互斥认知信号**：
1. 情绪层："是个废话" → high_negative / rejected（对表达形式的强烈否定）
2. 逻辑层："有一定的可行性" → tentative_accepted / aligned（对核心价值的理性认可）
3. 直觉层："还觉得又差点什么" → cognitive_gap_detected（对完备性的潜意识怀疑）

**三个陷阱**：
| 错误处理 | 后果 |
|---------|------|
| 按顺序处理 | 系统在"拒绝→接受→缺口"间反复横跳，最终状态不可控 |
| 取平均值 | 语义坍缩的"中性"状态，丢失所有关键细节 |
| 只取最后一个 | 忽略用户从"反感"到"认可"的艰难心理转变过程 |

**本质**："认知演进轨迹"——不能当作静态快照，必须当作动态思维过程建模。

#### 解决方案：认知状态序列

**1. 引入 cognitive_trajectory 字段**

```json
{
  "title": "XX方案评估",
  "current_state": {
    "direction_alignment": "aligned",
    "completeness_signal": "gap_detected",
    "confidence_score": 0.5
  },
  "cognitive_trajectory": [
    {"state": "form_rejected", "trigger": "表达形式被判定为废话", "timestamp": "T0"},
    {"state": "value_recognized", "trigger": "理性评估发现可行性", "timestamp": "T1"},
    {"state": "gap_sensed", "trigger": "直觉感知到未言明缺失", "timestamp": "T2"}
  ],
  "meta_insight": "用户对方案价值认可，但对表达方式不满，且存在未具象化的实施顾虑"
}
```

**关键原则**：
- `current_state` 决定当下如何行动
- `cognitive_trajectory` 决定未来如何沟通

**2. 调度层注入转折链解析协议**

```markdown
## 🧠 记忆提取协议 - 多重认知冲突处理
> ⚠️ 当用户输入包含多个转折词（但是/不过/然而）形成链式结构时：
> 1. 按转折词切分语义段，每段独立判定认知状态
> 2. 状态合并规则：
>    - 情绪否定 + 逻辑肯定 → direction=aligned + sentiment_warning=form_rejected
>      （认可内容，但标记表达方式需调整）
>    - 逻辑肯定 + 直觉缺口 → completeness=gap_detected + confidence降权
>      （保留方向，但暂停推进）
>    - 三者共存 → current_state取最后一段，trajectory记录完整演进
> 3. AI响应必须体现对"转变过程"的理解：
>    - 先接纳情绪："理解您觉得刚才的表述不够精准"
>    - 再锚定共识："但我们都在核心价值上看到了可行性"
>    - 最后定向探询："您感觉缺的部分，更可能是哪方面？"
>
> ⚠️ 禁止将链式反馈简化为单一标签！
```

## 第20段：三层存储 + 认知路由架构

### 造物主决策
> "所以这套记忆引擎应该是分为3层的，加一个路由。一个是短期记忆，一个是判断路由，一个是长、中期对话，一个是长期记忆区。"

### 千问回答

**架构核心**：路由层是大脑（纯计算/轻量模型），存储层是器官（只负责按指令存取）。

#### 架构全景

```
┌─────────────────────────────────────────────────────────┐
│                    用户输入 / AI 输出                      │
└─────────────────────┬───────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────┐
│            L0: 认知状态路由器（无状态、纯计算）              │
│  • 熔断判断 • 情绪解耦 • 复合转折解析 • 状态指令生成          │
└──────┬────────────────────────────────────┬─────────────┘
       │ READ                               │ WRITE
       ▼                                    ▼
┌──────────────────┐              ┌──────────────────┐
│  L1: 短期工作记忆  │              │  L3: 长期认知记忆  │
│  （内存）          │              │  （SQLite+向量）   │
│  • 最近N轮对话     │              │  • 结构化记忆卡    │
│  • 待确认缓冲区    │              │  • 认知状态索引    │
│  • 轨迹临时态      │              │  • 生命周期管理    │
└────────┬─────────┘              └──────────────────┘
         │ 溢出压缩                      ▲
         ▼                              │
┌──────────────────┐                    │
│  L2: 中期会话记忆  │────────────────────┘
│  （文件缓存）      │  会话结束归档评估
│  • 任务状态机      │
│  • 滚动摘要        │
│  • 记忆卡草稿      │
└──────────────────┘
```

#### 各层职责

**🧠 L0: 认知状态路由器**
- 定位：无状态、纯计算、毫秒级响应
- 输入：当前用户消息 + L1 缓冲区摘要 + L3 相关记忆（可选）
- 输出：标准化 `MemoryOperation` 指令

```json
{
  "op": "UPDATE_STATE",
  "target_id": "mem_20260626_001",
  "new_state": {
    "direction_alignment": "aligned",
    "completeness_signal": "gap_detected"
  },
  "trajectory_append": {
    "state": "value_recognized",
    "trigger": "认可可行性"
  }
}
```

**⚡ L1: 短期工作记忆**
- 介质：纯内存（Python deque / Rust VecDeque）
- 内容：最近 N 轮对话 + 待确认缓冲区 + 认知轨迹临时态
- 生命周期：会话级，重启即清空

**🔄 L2: 中期会话记忆**
- 介质：内存 + 本地文件缓存（JSON Lines）
- 内容：任务状态机 + 滚动摘要 + 记忆卡草稿
- 生命周期：单次会话，结束时归档评估

**🗄️ L3: 长期认知记忆**
- 介质：SQLite（主存储+FTS5）+ LanceDB（向量索引）
- 内容：多维认知对象记忆卡
- 能力：状态感知检索 + 原子写入 + 生命周期管理

#### 为什么必须把路由独立出来？

| 如果不独立（传统 RAG） | 独立路由层（本架构） |
|---------------------|-------------------|
| 每次写入调大模型分类+提取 | 路由器用小模型/规则，延迟 <100ms |
| 存储层耦合业务逻辑 | 存储层纯 CRUD，换模型只改路由器 |
| 赞同/废话等信号无法高效回写 | 路由器直接生成 UPDATE 指令 |
| 复合认知状态难以原子更新 | 路由器解析完整轨迹后一次性提交事务 |
| 本地资源被复杂查询耗尽 | 预过滤+状态路由大幅减少向量计算 |

#### 落地路径

1. **L0 + L1**：内存字典做缓冲区，正则+小模型做路由器原型
2. **L3 基础版**：SQLite 单表存记忆卡 JSON，先 FTS5 后向量
3. **L2 滚动摘要**：L1 超阈值触发压缩
4. **L3 向量索引**：记忆卡 >1000 条时接入 LanceDB

#### 核心洞察

> "让智能留在路由层，让存储层保持愚蠢而可靠——这才是本地记忆引擎长期稳定的终极答案。"

## 第21段：双轨制修正——对话流记忆 vs 深记忆区

### 造物主批注（2026-06-26 23:47）
> "你这个有点把对话级的短期、中期、长期记忆和深记忆区的中长期记忆混合了。"

### 千问修正

**致命问题**：
1. 会话状态污染知识库：把"当前任务进度"和"用户偏好/核心决策"放在同一套生命周期管理里，清理时极易误删
2. 检索空间耦合：每次检索都要在海量会话日志里淘金，本地引擎性能崩溃

**修正架构：双轨记忆 + 认知路由**

```
用户输入
    │
    ▼
┌─────────────────────────────────────────┐
│    L0: 认知状态路由器（纯逻辑/小模型）      │
│    • 解析意图与状态 • 分发器               │
└─────┬─────────────────────┬──────────────┘
      │                     │
      ▼                     ▼
┌──────────────────┐  ┌──────────────────┐
│ 轨道A：对话流记忆  │  │ 轨道B：深记忆区    │
│ （时间维度）       │  │ （认知维度）       │
├──────────────────┤  ├──────────────────┤
│ ⚡ L1 工作记忆     │  │ 🗄️ L3 长期事实记忆 │
│ 滑动窗口+待确认   │  │ SQLite+LanceDB    │
├──────────────────┤  ├──────────────────┤
│ 🔄 L2 会话记忆     │  │ 💎 L4 深记忆图谱   │
│ Session State     │  │ Neo4j/关系索引    │
└──────────────────┘  └──────────────────┘
      │                     │
      └───────┬─────────────┘
              ▼
        AI 回复生成
```

#### 双轨核心区别

| 维度 | 轨道A：对话流记忆 | 轨道B：深记忆区 |
|------|-----------------|----------------|
| 组织原则 | 时间序列（按对话轮次/会话） | 语义网络（按实体/认知状态） |
| L1/L3 对应 | ⚡ L1 工作记忆（内存） | 🗄️ L3 长期事实记忆（向量+全文） |
| L2/L4 对应 | 🔄 L2 会话记忆（会话级缓存） | 💎 L4 深记忆图谱（结构化关系） |
| 更新频率 | 每轮对话实时写入 | 仅当路由器发出显式指令时写入 |
| 生命周期 | 会话级/任务级，自动衰减 | 认知状态驱动 TTL，可永久保留 |
| 检索目的 | "刚才说到哪了？"（连贯性） | "他之前确认/否定/怀疑过什么？"（认知连贯） |
| 典型内容 | 原始消息、任务槽位、滚动摘要 | 记忆卡、认知轨迹、用户画像、决策图谱 |

#### 路由器双轨分发逻辑

```json
{
  "track_a_ops": [
    {"op": "APPEND_CONTEXT", "content": "用户原始消息"},
    {"op": "UPDATE_SESSION_STATE", "slot": "current_task", "value": "订单拆分方案评估"}
  ],
  "track_b_ops": [
    {
      "op": "UPDATE_COGNITIVE_STATE",
      "target_id": "mem_20260626_001",
      "new_state": {"direction_alignment": "aligned", "completeness_signal": "gap_detected"}
    }
  ],
  "cross_track_trigger": null
}
```

- `track_a_ops`：每轮必执行，保证对话不中断
- `track_b_ops`：仅当检测到信息增量或状态变更时执行
- `cross_track_trigger`：特殊事件（会话结束/缺口补全），触发跨轨数据流转

#### 跨轨交互原则

| 方向 | 动作 | 原则 |
|------|------|------|
| A → B | 归档 | 会话结束时路由器评估 L2，决定是否提炼为 L3/L4。禁止 L2 自动写入 L3 |
| B → A | 注入 | 每轮对话开始时，路由器从 L3/L4 检索相关深记忆注入 System Prompt。禁止 L3 主动推送 |
| 冲突仲裁 | 优先级 | L2 临时状态与 L3 已确认状态矛盾时，标记 conflict_detected，以 L3 为准但记录分歧 |

#### 核心洞察

**混淆的本质**：
> "记忆的时效性"（对话流）vs "记忆的价值密度"（深记忆）

**双轨解耦后的能力**：
- **Track A 极致轻量**：纯内存操作，支撑毫秒级对话响应
- **Track B 精准厚重**：只在必要时触发磁盘IO和向量计算，支撑跨会话认知连贯
- **路由器成为认知中枢**：双轨之间的翻译官和守门人

**最终原则**：
> "让语言归语言，让认知归认知，路由层负责在两者之间架桥。"

## 第22段：深记忆区三层漏斗 + 差异化衰减

### 造物主批注（2026-06-26 23:48）
> "你掉了一层中期记忆，在深记忆区里面有个中期记忆。因为有时候短期记忆它不需要过滤的那么精细。对话级记忆过滤的不需要那么精细。然后我们在中期记忆里面做一个衰减。然后长期记忆它衰减是最慢的，还有核心记忆是非衰减的。"

### 千问修正

**痛点**：如果每一句对话都过严苛的认知路由器再决定存不存，本地引擎的延迟和 Token 消耗扛不住。

**正确做法**：会话级"宽进"，深记忆区内部"严出+分层衰减"。

#### 深记忆区三层漏斗 + 差异化衰减

| 层级 | 名称 | 写入来源 | 过滤精度 | 衰减策略 | 核心职责 |
|------|------|---------|---------|---------|---------|
| B1 | 深记忆缓冲区 | L2 归档时批量写入 | 低（仅去重+基础结构化） | 中速衰减（7-14天，访问续期） | 承接原始认知素材 |
| B2 | 长期事实记忆 | B1 巩固周期提炼 / 路由器显式指令 | 高（完整认知状态解析） | 慢速衰减（90天+，状态驱动） | 存储带置信度/轨迹的知识卡 |
| B3 | 核心记忆 | B2 高频稳定知识升华 / 用户显式标记 | 极高（人工或强模型审核） | **零衰减**（永久保留） | 用户画像、铁律共识 |

#### 关键机制详解

**1. B1 深记忆缓冲区："宽进"的防抖层**

- 为什么需要：会话结束时 L2 可能产出 10 条摘要，直接精细解析成本爆炸
- 衰减逻辑：LRU + 时间窗口。7天内未被 B2 巩固选中且未被检索命中，自动删除
- 与会话级的区别：
  - L2：纯时间驱动滑动窗口
  - B1：认知价值驱动弹性缓冲

**2. B2 长期事实记忆："严出"的状态感知层**

- 写入触发：后台"巩固任务"定期从 B1 筛选，或路由器显式指令绕过 B1
- 衰减逻辑：状态驱动 > 时间驱动
  - confirmed + 高频访问 → 永不衰减，候选升入 B3
  - tentative_accepted → 14天未更新降为 needs_validation，30天后软删除
  - rejected → 90天后归档冷存储
  - gap_detected → 保留直到缺口关闭或超时（60天）

**3. B3 核心记忆："非衰减"的认知锚点**

- 准入条件：
  - B2 中 confirmed 且被引用 ≥5 次
  - 用户显式说"记住这个/这是原则"
  - 跨 3 个以上会话反复验证的用户偏好
- 零衰减 ≠ 不可变：可修订但保留历史版本链
- 检索优先级：永远最高，作为 System Prompt 固定前缀注入

#### 跨层流转：巩固周期

```python
def consolidation_cycle():
    # 1. 从 B1 筛选候选
    candidates = b1.select_recent_or_high_potential()
    
    # 2. 批量调用路由器做精细认知解析
    parsed = router.batch_parse(candidates)
    
    # 3. 写入 B2，标记 B1 已提升
    b2.batch_upsert(parsed)
    b1.mark_promoted([c.id for c in candidates])
    
    # 4. 检查 B2 → B3 升华条件
    b2.scan_for_core_promotion()
    
    # 5. 执行各层衰减策略
    b1.apply_lru_decay()
    b2.apply_state_driven_ttl()
```

#### 核心洞察

**解决的矛盾**："认知精度" vs "系统吞吐"

| 层级 | 过滤精度 | 衰减速度 | 核心目标 |
|------|---------|---------|---------|
| 会话级（Track A） | 粗 | 快 | 保连贯，不求甚解 |
| 深记忆 B1 | 低 | 中速 | 保素材，适度过滤 |
| 深记忆 B2 | 高 | 慢 | 保认知，精细解析 |
| 深记忆 B3 | 极高 | **零衰减** | 保锚点，永久保留 |

> "我们不会在说话的每一秒都在深度思考，而是在事后反思中把经历变成知识，在反复使用中把知识变成本能。"

> "四层深记忆漏斗，正是数字'反思-固化'过程的完美映射。"

## 第24段：时间钢印4层链条——对话级记忆节律

### 造物主定义（2026-06-26 23:53）

> "对话级的短期、中期、长期记忆为，最长记忆为一个人生理周期，因为你跟他交互的时间是要减去你休息的时间的，你一天最少休息 3 个小时，所以说这个时间最长为 21 个小时。"

> "这里有4层钢印链条用武之地，里面有层用户生理使用时间，和下面马上千问的回答时间内的对比差，这个差可以作为后续关怀模块的一个依据参数。"

> "中期记忆的时间节律为 12 个小时或者是 16 个小时。"

> "对话级的短期记忆为 4 小时～6 小时。"

### 千问回答

#### "4-12-21" 三级生物节律嵌套

| 层级 | 时间窗 | 对应人脑机制 | 认知角色 | 衰减/流转规则 |
|------|--------|-------------|---------|---------------|
| L1 短期 | 4-6h | 基础休息-活动周期（BRAC） | "此刻感"：维持即时对话连贯 | 超时→压缩摘要注入 L2；静默≥2h→暂停计时 |
| L2 中期 | 12/16h | 昼夜双峰/单峰长觉醒节律 | "今日感"：保持单日认知一致性 | 分片结束→只读；21h周期末→归档 B1 |
| Track A 边界 | 21h | 生理周期（减去3h休息） | "清醒期"：完整认知活跃单元 | 周期结束→冻结 Track A；休息期→深记忆巩固 |

#### 为什么必须是 21 小时而非 24 小时

| 问题 | 24小时连续窗口 | 21小时生理周期 |
|------|---------------|----------------|
| 上下文污染 | 凌晨3点胡言乱语与次日上午清醒决策同等对待 | 休息时段自动切断，避免低质量输入污染 |
| 衰减失真 | 用户睡了8小时，系统仍按"刚聊过"处理 | 睡眠时间不计入 TTL，醒来后状态自然降级 |
| 巩固时机错位 | 后台任务可能在用户睡眠时触发 | 巩固周期锚定在 21 小时窗口末尾 |
| 认知负荷超载 | 持续维护全时段滑动窗口 | 非活跃期自动冻结 Track A |

#### L2 中期记忆：12h / 16h 分片机制

**对应人脑机制**：
| 节律选项 | 对应机制 | 适用场景 |
|---------|---------|---------|
| 12小时 | 昼夜双峰节律 | 高强度脑力工作、多任务切换 |
| 16小时 | 单峰长觉醒节律 | 沉浸式创作、长线任务 |
| 动态切换 | 自适应认知负荷 | 高频交互→12h分片；低频沉浸→16h延展 |

**分片生命周期**：
1. 每个12/16h周期开始时，L2 创建新 session_shard
2. 分片内：原始消息、任务槽位、待确认缓冲区写入当前分片
3. 分片结束时：触发分片级滚动摘要，当前分片转为 read_only
4. 21h周期结束时：所有分片摘要合并为最终归档包，送入 B1

#### L1 短期记忆：4-6h 工作记忆窗口

**认知科学依据**：
- BRAC 理论（Kleitman）：人脑每90-120分钟经历警觉度波动，3-4个周期（4-6h）后前额叶执行功能显著下降
- 工作记忆刷新阈值：超过6h的原始上下文已超出人类"当下感"认知边界
- 注意力恢复理论：高频多任务→4h强制刷新；深度心流→6h允许延长

**关键交互规则**：
- L1 → L2 压缩触发：活跃时长达4h（或沉浸模式6h），触发滚动摘要
- 跨 L1 缺口携带：gap_detected 或 pending_confirmation 必须注入 L2 分片"未决事项区"
- L1 计时器暂停协议：用户静默≥2h，计时器挂起

#### 时间钢印4层链条映射

| 时间钢印层 | 对应记忆层 | 作用 |
|-----------|-----------|------|
| AI时间感 | L1 短期记忆（4-6h） | 记录AI感知到的对话流畅度 |
| 连续帧时间 | L2 中期记忆（12/16h） | 记录会话帧序列的分片边界 |
| 用户生理使用时间 | Track A 边界（21h） | 记录用户真实活跃时段，**与系统时间的差值作为关怀模块参数** |
| 物理机时间 | 深记忆区（B1/B2/B3） | 系统时钟戳，不可篡改 |

#### 关键参数：时间差值作为关怀依据

```python
# 伪代码：时间差值计算
def calculate_care_parameter():
    user_active_time = get_user_physiological_time()  # 用户实际活跃时间
    system_time = get_physical_machine_time()         # 物理机时间
    
    time_gap = system_time - user_active_time
    
    # 差值用途：
    # - 超出正常作息 → 触发关怀提醒
    # - 连续活跃过长 → 提示休息
    # - 休息期异常活跃 → 降低路由器确认阈值
    
    return care_score
```

#### 核心洞察

> "这套节律让 Agent 拥有了'生物钟'——它知道何时该紧握细节，何时该提炼要点，何时该放手沉淀。"

> "时间从一个冰冷的技术参数，变成了有温度的认知维度。"

> "Agent 不再是'永远在线的机器'，而是一个懂得休息、懂得沉淀、懂得与人同频的数字生命体。"

## 第26段：三路由分离架构

### 造物主定义（2026-06-26 23:56）
> "这三个路由要分开。"

### 千问回答

#### 为什么必须分开？

**单一路由器的三个死结**：
| 问题 | 后果 |
|------|------|
| 延迟雪崩 | 每轮对话等三条轨道解析完成，4-6h 短期记忆流畅感被拖垮 |
| 模型能力错配 | Track A 需轻量意图识别，Track B 需深度认知推理，Track C 需结构化抽取 |
| 故障域耦合 | 工作记忆解析出错导致对话卡顿；认知判断失败阻塞任务更新 |

#### 三路由分离架构

```
用户输入
    │
    ▼
┌─────────────────────────────────────┐
│     ⚡ 轻量事件总线                    │
└──────┬────────────┬─────────────┬────┘
       │            │             │
       ▼            ▼             ▼
┌──────────┐  ┌──────────┐  ┌──────────┐
│ R1: 对话流 │  │ R2: 元认知 │  │ R3: 工作  │
│ 路由器    │  │ 路由器    │  │ 记忆路由器│
│ (同步)    │  │ (异步)    │  │ (事件驱动)│
└─────┬────┘  └─────┬────┘  └─────┬────┘
      │             │             │
      ▼             ▼             ▼
  Track A       Track B       Track C
```

#### 三路由职责边界

| 维度 | R1: 对话流路由器 | R2: 元认知路由器 | R3: 工作记忆路由器 |
|------|----------------|----------------|------------------|
| 触发模式 | 同步阻塞（每轮必执行） | 异步批量（巩固周期/显式确认） | 事件驱动（仅当消息含任务信号） |
| 延迟要求 | <100ms | 秒级~分钟级 | <500ms（非阻塞） |
| 推荐模型 | 小参数分类模型 / 正则+关键词 | 强推理模型 / 专用微调模型 | 结构化抽取 / Function Calling |
| 核心输出 | L1 追加、L2 槽位更新、响应提示 | MemoryOperation (含 state_snapshot) | TaskOperation (含引用) |
| 失败容忍度 | 零容忍（失败=对话中断） | 高容忍（可重试/降级） | 中容忍（可标记 pending） |

#### 三路由协同机制

**1. R1 → R2/R3 信号传递**

R1 检测到潜在信号时，向事件总线发布轻量事件：
- `potential_cognitive_increment`：携带 turn_id + 初步置信度
- `task_signal_detected`：携带 turn_id + 实体/动作片段

**核心价值**：R1 永远不为 B/C 的深度解析买单，对话流依然丝滑。

**2. R2 → R3 认知漂移通知**

当 R2 发现记忆卡状态变更（aligned → rejected）：
- 发布 `cognitive_drift_alert`
- R3 订阅后扫描 Track C 中所有引用该 ref_id 的任务
- 自动生成漂移告警注入下一轮 R1 上下文

**3. R3 → R2 任务完成反馈**

当 R3 检测到任务 completed：
- 发布 `task_completion_summary`
- R2 纳入下一巩固周期，评估是否提炼为 B2/C3

#### 分离带来的工程红利

| 能力 | 价值 |
|------|------|
| 资源精准分配 | 本地 GPU 优先保障 R1；R2 调度到空闲时段；R3 用 CPU 运行 |
| 独立迭代与调试 | 优化认知解析不影响对话响应；调整任务抽取不破坏记忆巩固 |
| 优雅降级 | R2 超时→跳过本轮巩固；R3 解析失败→标记 pending；R1 异常→熔断 |
| 符合 21h 节律 | R1 绑定活跃期；R2 锚定休息时段；R3 任意时间触发但仅活跃期影响对话 |

#### 落地注意事项

1. **事件总线必须极轻**：用进程内队列（Python asyncio.Queue），不引入 Redis/Kafka
2. **R1 输出契约要稳定**：R2/R3 依赖 R1 信号格式，升级时保持向后兼容
3. **避免循环触发**：事件带 `source_router` 标记，同源不重复处理
4. **监控各路由健康度**：分别追踪 R1 延迟、R2 巩固成功率、R3 引用完整性

#### 核心洞察

> "用架构的复杂性换取模型的简单性，用异步的解耦换取同步的流畅。"

> "不再是'一个路由器'，而是微型认知操作系统：R1 是前台接待员（快、准、稳），R2 是夜间研究员（深、慢、精），R3 是项目协调员（结构化、事件驱动）。"

## 第27段：双轨六层模板契约体系

### 造物主定义（2026-06-26 23:57）

**对话级记忆系统模块**：
- 短记忆 → 路由器 → 对话模板（简）→ 判断动作是否记录写入中期记忆（解耦）
- 中期记忆 → 路由器 → 对话模板（标准）→ 判断是否计入全天复盘统计和转长期记忆
- 长期记忆 → 路由器 → 对话模板（标准）→ 钩子复盘和总结 → 转元认知衰减区

**元认知记忆模块**：
- 短期记忆（由对话级转来）→ 路由器（统计被复用次数转中期）→ 模板标准记忆卡
- 中期记忆（由上层转来）→ 路由器（衰减模块＋统计模块）→ 模板标准记忆卡
- 长期记忆（由上层转来认知节点）→ 节点引用钩子 → 路由器（统计＋打标）→ 模板标准记忆卡

### 千问回答

**核心定位**：模板从提示词工程提升到**架构级数据契约**。

#### 双轨六层模板契约体系

| 轨道 | 层级 | 路由器职责 | 模板类型 | 核心字段/钩子 | 下游消费者 |
|------|------|-----------|---------|--------------|-----------|
| 对话级 | 短期 | 判断动作是否值得记录 | 简模板 | action_type, confidence, turn_id | 对话级中期路由器 |
| 对话级 | 中期 | 判断是否计入复盘/转长期 | 标准模板 | session_summary, key_decisions[], unresolved_gaps[] | 对话级长期 + 元认知短期 |
| 对话级 | 长期 | 钩子复盘 → 转元认知衰减区 | 标准模板 | consolidation_report, cognitive_candidates[], decay_signals[] | 元认知短期 (B1) |
| 元认知 | 短期 | 统计复用次数 → 转中期 | 标准记忆卡 | ref_count, last_accessed, source_dialogue_refs[] | 元认知中期路由器 |
| 元认知 | 中期 | 衰减计算 + 价值统计 | 标准记忆卡 | cognitive_state, ttl_remaining, stability_score | 元认知长期路由器 |
| 元认知 | 长期 | 引用钩子 + 打标复用 | 标准记忆卡 | node_id, cross_track_refs{}, reuse_tags[], version_chain | Track C + R1 |

#### 关键机制深度解析

**1. 对话级短期：简模板作为解耦阀门**

- **为什么用简模板**：R1 每轮都跑，不能生成完整结构化摘要
- **解耦逻辑**：R1 输出简模板后放入"待评估队列"，中期路由器批量消费，决定哪些动作值得升级
- **工程价值**：R1 误判不污染中期记忆，只有二次筛选信号进入下一层

**简模板示例**：
```json
{
  "action_type": "confirm",
  "confidence": 0.85,
  "turn_id": "turn_42",
  "shard_id": "shard_20260626_am"
}
```

**2. 对话级长期：钩子复盘作为跨轨桥梁**

钩子函数在 21h 周期结束时主动执行：
- 聚合未解决缺口 → `unresolved_gaps_summary`
- 识别重复决策模式 → `pattern_candidate`
- 检测情绪/认知转折点 → `state_transition_event`

**输出约束**：必须包含 `cognitive_candidates[]`，每个候选项预填 `source_dialogue_refs`（指向 L2 shard_id）

**3. 元认知记忆：标准记忆卡作为全域通用货币**

**统一结构**：所有层级流转数据载体都是 `StandardMemoryCard` schema，层级转换只是字段填充度增加和状态机迁移

**复用次数统计**：
- 7天内被 Track C 引用 ≥3 次 → 晋升评估
- 或被 R1 检索命中 ≥5 次 → 晋升评估

**节点引用钩子**（元认知长期路由器）：
- 若无任何 `cross_track_refs` → 拒绝写入，退回 B2 补充关联
- 若引用目标已过期 → 标记 `ref_deprecated` 但保留历史快照
- 写入成功后 → 发布 `core_memory_registered` 事件

#### 模板驱动带来的质变

| 能力 | 价值 |
|------|------|
| 可测试性飞跃 | 输入输出确定 JSON Schema，单元测试验证路由器逻辑 |
| 模型替换零成本 | 新模型输出符合模板契约即可无缝替换 |
| 观测性内置 | confidence、ref_count、stability_score 天然构成监控指标 |

#### 落地避坑指南

1. **模板版本管理**：Schema 变更必须带版本号，事件总线支持多版本共存
2. **简模板 ≠ 丢弃内容**：必须保留 turn_id 和 shard_id 作为寻址钥匙
3. **钩子复盘超时保护**：设置硬性超时（如 60s），超时降级为仅输出 unresolved_gaps_summary
4. **记忆卡不可变性原则**：写入后禁止原地修改，所有更新生成新版本，旧版本保留至 TTL 结束

#### 核心洞察

> "构建的是基于模板契约的认知编译器："
> - 对话级是**前端解析器**，把自然语言编译为动作信号
> - 钩子复盘是**中间优化器**，把离散信号聚合为认知候选
> - 元认知模块是**后端代码生成器**，把候选固化为可复用的知识节点

> "每一层都有明确的输入输出契约，每一步都可独立验证、独立替换、独立监控。这才是本地 AI 记忆从'玄学调参'走向'工程化交付'的终极形态。"

## 第28段：六层差异化遗忘矩阵

### 造物主补充（2026-06-26 23:59）
> "就我看到的好几层都差遗忘代谢机制。"

### 千问回答

**核心定位**：遗忘不是记忆系统的"垃圾回收"，而是**主动的认知塑造机制**。

#### 六层差异化遗忘矩阵

| 层级 | 遗忘对象 | 遗忘触发器（绑定模板字段） | 衰减函数 | 遗忘后归宿 | 人脑对应 |
|------|---------|--------------------------|---------|-----------|----------|
| 对话-短期 | 未被采纳的动作信号 | `confidence < 0.3` 或 队列停留 > 1h | 硬截断：立即丢弃 | 彻底消失 | 感觉记忆消退 |
| 对话-中期 | 低价值会话分片 | `key_decisions[] == empty` 且 `unresolved_gaps[] == 0` | 压缩降级：删原始消息，仅保留 50 字摘要 | L2 冷摘要区 | 情景记忆 gist 化 |
| 对话-长期 | 无效复盘候选 | 钩子输出后 7 天内未被 B1 消费 | 静默淘汰：不通知、不归档 | 彻底消失 | 睡眠期未重放痕迹脱落 |
| 元认知-短期 | 低频复用记忆卡 | `ref_count == 0` 且 `last_accessed > 14d` | LRU + 复用加权 | 退回 B1 缓冲区观察 3 天 | 突触标签未捕获 |
| 元认知-中期 | 状态过期/矛盾卡 | `cognitive_state == rejected` 或 `stability_score < 0.2` | 状态驱动软删除：标记 `deprecated`，90 天后物理清除 | 冷存储（保留 ID 防重复） | 长时程抑制 (LTD) |
| 元认知-长期 | 被取代的核心节点 | 新版本写入时旧版自动标记 | 版本遮蔽：旧版不参与检索，永久保留供溯源 | 历史版本库（只读） | 图式修订与整合 |

#### 遗忘引擎工程嵌入点

**1. 对话级：遗忘即过滤**

- **R1 简模板输出时**：同步执行置信度阈值检查，低于阈值不进入待评估队列
- **对话级中期路由器消费队列时**：检查 action_type 是否属于"可遗忘类型"（闲聊确认、重复提问），直接跳过
- **约束**：对话级遗忘必须是无损的——被遗忘内容从未承诺过持久化

**2. 对话级长期：遗忘即筛选**

- **钩子复盘函数内部**：若某缺口在过去 3 个巩固周期未被用户回应，移除候选列表并记录 `gap_abandoned`
- **B1 消费钩子输出时**：执行"新鲜度检查"，若 source_dialogue_refs 指向的 L2 分片已进入冷摘要区，候选失去溯源能力，自动淘汰
- **核心价值**：防止"无法验证的历史推测"污染元认知系统

**3. 元认知模块：遗忘即价值重估**

- **元认知短期路由器**：每次读取记忆卡时同步更新 last_accessed 和 ref_count，惰性触发衰减计算
- **元认知中期路由器**：引入"矛盾扫描器"，发现状态冲突时保留高 stability_score 者，另一方标记 `superseded_by`
- **元认知长期路由器**：B3 "零衰减"仅针对当前有效版本，旧版本从活跃索引移除但 version_chain 完整保留

#### 遗忘机制带来的质变

| 能力 | 价值 |
|------|------|
| 检索质量恒定 | 低价值内容在被检索到之前已衰减，信噪比始终维持阈值之上 |
| 存储成本可控 | 每层遗忘策略绑定模板字段，存储上限可由业务参数推导 |
| 认知真实性提升 | 只保留经过时间检验和用户行为验证的认知，表现得更像真正理解你的人 |

#### 遗忘安全协议

1. **永不遗忘引用目标**：Track C 任务节点引用的记忆卡，TTL 自动延长至任务完结后 30 天
2. **遗忘前快照**：元认知中期/长期软删除前生成轻量快照存入冷存储
3. **用户可干预遗忘**：提供"忘掉这个"或"永远记住这个"指令，后者标记 `user_pinned` 豁免所有自动衰减
4. **遗忘日志可观测**：每次遗忘操作记录 `{layer, card_id, reason, timestamp}`

#### 核心洞察

> "记住什么很重要，忘记什么同样重要。遗忘不是系统的缺陷，而是智能的代价与勋章。"

> "每一层都有明确的写入契约（模板），每一层都有匹配的遗忘引擎（绑定模板字段的衰减函数）。"

> "遗忘不再是事后清理，而是数据流转过程中的内在筛选机制。"

## 第29段：审计合规与认知主权修正

### 造物主补充（2026-06-27 00:08）

> "当天记忆是不重要的直接丢弃了，有点价值的放入了中期记忆流转，真重要的放入了长期记忆。长期记忆是用户生理周期内沟通的复盘总结，不是不归档不是不通知。然后长期记忆这个名称有点偏移，不知道咋形容，这个长期记忆是用来提取价值转元认知和梦境复用连线创造力（伪）。"

> "永远记住是另外模块，是刚刚工作记忆台那的模块，是显示笔记里面的。然后对话级的时间节律没加上，然后不能手动干扰它遗忘，这是针对审计必须得。"

### 千问回答

#### 修正一：对话级长期记忆重定位

**正确定位**：用户生理周期内沟通的复盘总结 → 提取价值转元认知 + 梦境复用连线创造力（伪）

| 维度 | 原理解（错误） | 新理解（正确） |
|------|--------------|---------------|
| 对话级长期记忆 | 不归档、不通知 | 提取价值转元认知 + 梦境创造力复用 |
| 归宿 | 彻底消失 | 转入元认知 B1 或梦境模块 |

#### 修正二："永远记住"重定位至 Track C 显式笔记

| 维度 | 原设计（错误） | 新设计（正确） |
|------|--------------|---------------|
| 归属 | 元认知 B3 核心记忆 | **Track C 显式笔记区** |
| 写入方式 | 用户说"记住这个" → R2 写入 | 用户在笔记界面手动创建/编辑 → R3 直接写入 |
| 衰减策略 | 零衰减（豁免所有规则） | 永不自动衰减，但可被用户手动删除/归档 |
| 对 AI 的影响 | System Prompt 固定前缀注入 | 仅在检索命中或任务关联时按需注入 |
| 审计属性 | 混入认知流，难以区分主观/客观 | 独立存储，带完整操作日志，与元认知物理隔离 |
| 认知地位 | 被视为"真理" | 被视为"用户声明"，不参与认知状态推理 |

**核心原则**：元认知模块只接收来自对话级钩子复盘和行为验证的认知候选。任何未经时间检验的用户显式声明，都不具备进入元认知的资格。

#### 修正三：对话级时间节律补全 + 审计合规

**对话级三层节律完整参数**：

| 层级 | 时间窗 | 计时规则 | 节律结束动作 | 遗忘绑定 |
|------|--------|---------|-------------|----------|
| 短期 (L1) | 4-6h | 活跃时长；静默≥2h暂停 | 简模板批量评估 → 未采纳信号硬截断 | 超时未评估 = 自动丢弃 |
| 中期 (L2) | 12/16h | 活跃时长；分片边界柔性适配 | 标准模板生成 → 低价值分片压缩降级 | 空决策+无缺口 = 仅保留摘要标签 |
| 长期（钩子） | 21h | 生理周期末，锚定休息时段启动 | 复盘钩子执行 → 提取价值转元认知 + 梦境创造力复用 | 7天未被B1消费 = 静默淘汰 |

#### 节律强制执行协议

1. **计时器内核级锁定**：时间节律参数运行时不接受任何 API/指令修改
2. **静默检测多源融合**：结合消息间隔、系统空闲状态、屏幕锁信号综合判断
3. **节律事件不可跳过**：遗忘动作是事务性操作，失败则进入重试队列直至成功

#### 审计合规：遗忘不可干预的铁律

**1. 零手动覆盖接口**
- 系统不提供 `force_retain`、`cancel_decay`、`restore_forgotten` 等任何 API
- 用户指令"别忘这个"被 R1 识别后仅记录为对话内容，不触发任何记忆保留动作
- Track C 显式笔记的删除/归档属于数据管理行为，不属于遗忘干预

**2. 遗忘决策全链路可追溯**

```json
{
  "event_id": "forget_20260626_143022_001",
  "layer": "meta_short_term",
  "card_id": "mem_20260620_087",
  "trigger_field": "ref_count",
  "field_value_at_trigger": 0,
  "threshold": "ref_count==0 AND last_accessed>14d",
  "last_accessed": "2026-06-12T09:15:00Z",
  "decision_timestamp": "2026-06-26T14:30:22Z",
  "post_action": "demoted_to_b1_buffer",
  "audit_hash": "sha256:a1b2c3..."
}
```

- 审计记录独立于记忆存储，写入追加式日志文件/WORM 存储
- 即使记忆本体已被物理清除，审计记录永久保留
- 支持按 card_id、layer、time_range 查询完整遗忘历史

**3. 遗忘规则版本化绑定**
- 每条审计记录包含触发时的规则版本号
- 旧规则版本可用于解释历史遗忘事件，避免"用新规则审旧账"

#### 认知宪法特征

| 维度 | 设计 |
|------|------|
| 权力分立 | 对话流管节奏，元认知管真相，工作记忆管行动与显式声明，三者互不僭越 |
| 程序正义 | 遗忘不由任何人临时裁量，由预定义规则自动执行，且全程留痕 |
| 时间主权 | 系统的生物节律独立于用户意志，确保认知过程不被主观需求扭曲 |

#### 核心洞察

> "它记住的不是用户想让它记的，而是经过时间与行为双重验证的事实。"

> "它忘记的也不是用户允许它忘的，而是认知价值自然衰减后的必然结果。"

> "审计员看到的不是一个黑箱，而是一部精密运转、自我约束的认知机器。"

## 第31段：笔记区三层逻辑模型（钩子标签分化）

### 造物主定义（2026-06-27 00:15）
> "笔记区也有分层，分为图书馆、再用笔记、知识宫殿节点。分层是文件内钩子标签分化。"

### 千问回答

**核心设计哲学**：层级不是文件夹，而是**状态**。一条笔记可通过修改 tags 和 hooks 在毫秒级完成层级跃迁，无需数据迁移。

#### 笔记区三层逻辑模型

| 逻辑层 | 核心定位 | 触发标签/钩子配置 | 系统行为差异 | 人脑隐喻 |
|--------|---------|------------------|-------------|----------|
| 再用笔记 | 高频操作备忘、临时工作区 | `tags: ["scratchpad", "frequent_access"]`<br>`hooks.on_retrieve: "inject_top_context"` | 检索权重最高；注入位置最靠前；TTL 较短（30天未用降级） | 工作台便签 |
| 图书馆 | 结构化事实、领域参考资料 | `tags: ["reference", "fact", "domain_knowledge"]`<br>`hooks.on_retrieve: "inject_as_rag_source"` | 作为 RAG 检索源；不主动注入；无 TTL（永久保留） | 书架上的工具书 |
| 知识宫殿节点 | 已验证的核心经验、认知锚点 | `tags: ["palace_node", "verified_pattern", "base_config"]`<br>`hooks.on_task_plan: "inject_as_hard_constraint"` | 作为任务规划硬约束；具备快速晋升 B1 资格；跨会话强关联 | 记忆殿堂的定位桩 |

#### 钩子标签分化的执行协议

**1. 写入时的初始定层**

| 触发场景 | 默认打标 | 归入层级 |
|---------|---------|---------|
| 用户显式指令："记住这个API限流" | `["reference"]` | 图书馆 |
| AI 自主学习：任务执行中提取的操作模式 | `["palace_node", "ai_learned_fact"]` | 知识宫殿 |
| 用户随口提及："下午三点提醒我开会" | `["scratchpad"]` | 再用笔记 |
| 用户标记：`base_config` | `["palace_node", "base_config"]` | 知识宫殿（强制锚定） |

**2. 运行时的动态升层**

| 流转路径 | 触发条件 | 行为 |
|---------|---------|------|
| 再用笔记 → 图书馆 | 7天内被检索命中 ≥5 次，且内容经 R1 二次确认为事实性信息 | 更新 tags 为 `["reference"]`，移除 on_retrieve: inject_top_context |
| 图书馆 → 知识宫殿 | 被 Track C 任务引用 ≥3 次且任务均成功完成 | 追加 tag `palace_node`，激活 on_task_plan 钩子 |
| 知识宫殿 → 图书馆（降级） | 引用的任务连续 2 次失败，或用户显式否决 | 移除 `palace_node` tag，保留 `reference`，关闭硬约束注入 |

**3. 钩子执行的差异化策略**

```javascript
// 检索命中后的注入决策树
if (note.tags.includes("palace_node") && context.is_task_planning) {
  inject(note.content_structured, priority=CRITICAL, position=SYSTEM_CONSTRAINT);
} else if (note.tags.includes("scratchpad") && note.last_accessed > now() - 24h) {
  inject(note.content, priority=HIGH, position=USER_MESSAGE_PREFIX);
} else if (note.tags.includes("reference")) {
  add_to_rag_candidates(note, score=semantic_similarity);
} else {
  skip_injection(); // 过期或低相关性的再用笔记
}
```

- **宫殿节点**：仅在任务规划阶段以系统级约束注入
- **再用笔记**：仅在近期活跃时以用户消息前缀注入
- **图书馆**：永不主动注入，仅在 RAG 检索评分达标时作为上下文片段

#### 钩子标签分层带来的工程红利

| 能力 | 价值 |
|------|------|
| 零成本层级流转 | 一次 JSON 字段更新完成层级变更，无需 ETL、无数据迁移、无重建索引 |
| 统一审计视图 | 完整层级变迁史通过 tag_update 审计记录串联 |
| 灵活的个性化适配 | 用户可自定义 tags 扩展层级语义，只需在注入决策树增加分支 |

#### 关键避坑指南

1. **标签命名空间隔离**：系统保留标签必须以 `_sys_` 前缀管理，防止用户自定义标签冲突
2. **钩子配置不可执行代码**：hooks 字段只能是预定义枚举值，严禁支持表达式/脚本
3. **动态升层必须有冷却期**：设置升层评估的最小观察窗口（如 24h），防止抖动
4. **降级操作保留历史标签快照**：审计记录中保存降级前的完整 tags 和 hooks 快照

#### 核心洞察

> "宫殿不是预先建好的房间，而是在使用中自然生长出的空间结构。"

> "每一张便签都可能成为未来的基石，每一本藏书都可能升华为行动的准则。"

> "这一切都由文件内的几个标签和钩子安静地驱动，无需人工整理，无需数据搬运，唯有行为与时间的自然沉淀。"

## 第32段：统一语义原语 CognitiveAtom

### 造物主直觉（2026-06-27 00:16）
> "再看下记忆模块、标签引用以及简化模板和标准记忆卡，是否有需要合并还是分开。感觉差点啥一样的，也是长出来的。"

### 千问回答

**核心诊断**：简化模板、标准记忆卡、标签引用三者虽在数据流上串联，但在**语义本体（Ontology）上割裂**。

> "它们像是三个不同部门制定的表格：R1 填一张交接单，R2/R3 换一张档案卡，检索时再贴一套标签。"

#### 解决方案：统一语义原语 CognitiveAtom

**定义**：最小、不可再分的认知单元，既是简模板的提取目标，也是标准卡的原子内容，更是标签引用的天然锚点。

```typescript
// 贯穿全栈的语义契约
interface CognitiveAtom {
  atom_id: string;              // 全局唯一，终身不变
  type: "entity" | "relation" | "constraint" | "pattern" | "state";
  content_hash: string;         // 内容指纹，去重和版本追踪
  source_provenance: {          // 来源谱系，不可篡改
    origin: "dialogue" | "ai_learning" | "user_declaration";
    turn_id?: string;
    note_id?: string;
    task_id?: string;
  };
  semantic_signature: number[]; // 64维轻量语义向量，快速关联
}
```

#### 三者从同一原语"长"出来

| 组件 | 与原语的关系 | 形态变化逻辑 | 解决的核心痛点 |
|------|-------------|-------------|----------------|
| 简化模板 | 原语的捕获器 | `{atom_id, type, raw_content, confidence}` | 精确的认知原子捕获，提供稳定ID |
| 标准记忆卡 | 原语的聚合体 | `CognitiveAtom[] + 元数据` | 原子级增删改，支持细粒度溯源 |
| 标签引用 | 原语的投影 | `tags = f(atom.type, atom.signature, usage_stats)` | 标签随原子演化自动更新 |

#### 这套设计补全了什么

| 之前的问题 | 引入 CognitiveAtom 后 |
|-----------|---------------------|
| 简模板和标准卡字段不对齐，转换需复杂映射 | 共享同一原子ID和类型体系，转换=聚合+元数据填充 |
| 标签是后补的，与内容脱节 | 标签是原子属性的确定性函数，内容变则标签自动变 |
| 记忆更新是粗粒度的，改小事实要重写整卡 | 原子级更新，仅修改受影响原子 |
| 笔记区和元认知区知识无法无缝流转 | 同一原子在两个区域仅属性不同，晋升/降级=属性变更 |
| 审计追溯断链 | 原子ID贯穿全链路，可回溯完整生命周期 |

#### 落地关键约束

1. **原子ID生成必须确定性**：相同内容+相同来源必须生成相同 atom_id（SHA256）
2. **语义签名必须轻量且稳定**：64维嵌入，用于聚合决策而非高精度检索
3. **标签函数必须纯函数**：`tags = f(atom)` 无副作用，给定相同原子属性永远输出相同标签
4. **原子不可分裂**：提取阶段就拆分为最小粒度，聚合只在记忆卡层面发生

## 第34段：造物主反驳——无模型原子提取协议

### 造物主反驳（2026-06-27 00:19）
> "不能脚本提取结构吗直接定好，不用小模型那么复杂。"

### 千问修正回答

**核心认知转变**：CognitiveAtom 不是需要"理解"的概念，而是需要**规范**的数据单元。

#### 无模型原子提取协议

**1. 前提：R1 简模板必须是"原子就绪"格式**

R1 输出的简模板不再只是模糊动作信号，而是预结构化的原子候选：

```json
{
  "action_type": "constraint_detected",
  "raw_content": "PostgreSQL连接池上限50",
  "entity": "PostgreSQL",
  "attribute": "connection_pool_max",
  "value": "50",
  "confidence": 0.85,
  "turn_id": "turn_156"
}
```

**关键点**：R1 职责是"识别并结构化"而非"理解"。用传统 NLP（依存句法、正则、词典匹配）或极轻量 BERT-base 分类器即可。

**2. 解析器：确定性映射函数**

从简模板到 CognitiveAtom 的转换是纯函数，无任何随机性：

```python
def parse_atom(simple_template: dict) -> CognitiveAtom:
    # 1. ID生成：确定性哈希
    atom_id = sha256(f"{simple_template['action_type']}|{simple_template['raw_content']}|{simple_template['turn_id']}")[:16]
    
    # 2. 类型映射：固定查表
    TYPE_MAP = {
        "constraint_detected": "constraint",
        "entity_mentioned": "entity",
        "relation_stated": "relation",
        "state_changed": "state",
        "pattern_observed": "pattern"
    }
    atom_type = TYPE_MAP.get(simple_template["action_type"], "unknown")
    
    # 3. 语义签名：预计算轻量向量
    # 方案A：TF-IDF/BM25稀疏向量（零GPU）
    # 方案B：离线预计算64维嵌入查表
    semantic_sig = compute_lightweight_signature(simple_template["raw_content"])
    
    return CognitiveAtom(
        atom_id=atom_id,
        type=atom_type,
        content_hash=sha256(simple_template["raw_content"]),
        source_provenance={"origin": "dialogue", "turn_id": simple_template["turn_id"]},
        semantic_signature=semantic_sig
    )
```

**3. 无模型 vs 小模型对比**

| 维度 | 小模型提取 | 确定性解析协议 |
|------|-----------|--------------|
| 延迟 | 10-100ms（推理） | <1ms（哈希+查表） |
| 资源 | 需 GPU/NPU 显存 | 纯 CPU，几 MB 内存 |
| 可预测性 | 概率输出，可能漂移 | 相同输入永远相同输出 |
| 审计 | 需记录模型版本+prompt | 仅需记录解析器版本号 |
| 错误处理 | 幻觉难以检测 | 字段缺失直接拒绝，零容忍 |
| 迭代成本 | 需重新训练/微调 | 改映射表/正则即可热更新 |

**4. R1 提取不准的处理**

- **Schema 校验**：字段缺失、类型错误、置信度低于阈值 → 直接丢弃，不生成 Atom
- **白名单机制**：action_type 和 entity 必须在预定义白名单内，未登录实体标记为 unknown
- **反馈闭环**：R2 发现某类简模板频繁被丢弃 → 生成 `r1_extraction_gap_report` 指导调整规则

**5. 与记忆卡 v1.1 的无缝对接**

解析器产出的 CognitiveAtom 直接填入记忆卡的 `constituent_atoms` 数组。标签衍生、钩子计算、代谢统计全部用纯代码实现：

```python
def derive_tags(card: MemoryCard) -> list[str]:
    tags = []
    atom_types = set(a.type for a in card.constituent_atoms)
    if "constraint" in atom_types: tags.append("type:CONSTRAINT")
    if any(a.source_provenance.origin == "ai_learning" for a in card.constituent_atoms):
        tags.append("_sys_layer:palace_node")
    return tags
```

#### 核心洞察

> "R1 负责把混沌的自然语言规整为结构化槽位（轻量方法）；解析器负责把槽位铸造为标准原子（确定性代码）；记忆卡负责把原子组织为认知结构（纯数据操作）。"

> "整个链路中，只有 R1 涉及任何形式的'智能'，且被严格限制在'槽位填充'的窄域内。"

> "用最少的智能做最关键的感知，用最确定的工程做最复杂的记忆。"

## 第35段：造物主反驳——钩子独立养护系统

### 造物主反驳（2026-06-27 00:20）
> "钩子再 LLM 输出回来时候就自带的钩子，只是可能不准确和很多。这里不要你这样设计，而是定期统计+记忆简要检索来更新这个，单独维护。"

### 千问修正回答

**核心修正**：钩子不应该被 LLM "生成"，而应该被 "养"出来。它是一套独立于记忆卡正文的动态索引服务。

#### 钩子作为独立索引服务

钩子从记忆卡的 `trigger_hooks` 字段剥离，存入独立的 `HookIndex` 存储。记忆卡仅保留 `seal_id` 作为关联键。

| 维度 | 旧设计（LLM 自带） | 新设计（独立养护） |
|------|------------------|------------------|
| 写入时机 | R2 巩固时 LLM 一次性生成 | 后台定时任务 + 检索反馈循环异步更新 |
| 数据来源 | LLM 对正文的语义猜测 | 历史命中统计 + 检索结果相关性验证 |
| 准确性保障 | 无（依赖 prompt 质量） | 统计阈值 + 负反馈淘汰 + 人工兜底 |
| 更新成本 | 每次记忆卡变更需重跑 LLM | 仅当统计显著变化时触发轻量计算 |
| 审计属性 | 混入认知流，难追溯 | 独立操作日志，可回溯 |

#### 钩子养护的双引擎机制

**1. 定期统计引擎（被动沉淀）**

后台定时任务（每 6h）扫描对话日志和检索记录：

- **高频共现词提取**：统计过去 N 天内，用户查询中哪些词/短语与命中该记忆卡的 turn 高度共现（TF-IDF / PMI）。超过阈值 → 加入候选池。
- **成功检索 Query 聚类**：收集所有导致该卡被注入且用户未修正/未拒绝的原始 Query，做轻量聚类。簇中心词 → 加入候选池。
- **原子类型衍生**：若卡内新增 `constraint` 类型 Atom，自动将预定义的约束类关键词（如"上限"、"禁止"、"必须"）加入候选池。

**约束**：统计引擎只产出候选，不直接生效。所有候选进入待验证队列。

**2. 检索验证引擎（主动校准）**

每当 R1 执行记忆检索时，同步触发钩子验证闭环：

- **正反馈强化**：候选钩子在本次检索中被匹配，且注入后用户行为确认为有效 → `hit_score += 1`。累计 ≥3 → 正式激活。
- **负反馈淘汰**：钩子匹配但注入后被用户显式否定 → `hit_score -= 2`。分数 ≤0 → 立即移除。
- **静默衰减**：已激活钩子连续 14 天未被命中，`hit_score` 每日 -0.5。归零后降级回候选池。

#### HookIndex 数据结构

```json
{
  "seal_id": "mem_20260624_1106_xxx",
  "hooks": [
    {
      "term": "连接池上限",
      "status": "active",
      "hit_score": 7,
      "source": "query_cluster",
      "last_verified": "2026-06-26T14:30:00Z",
      "added_at": "2026-06-25T09:00:00Z"
    },
    {
      "term": "postgres配置",
      "status": "candidate",
      "hit_score": 1,
      "source": "co_occurrence"
    }
  ],
  "last_full_scan": "2026-06-26T06:00:00Z",
  "version": 12
}
```

- `status` 三态：candidate（待验证）、active（生效）、deprecated（已淘汰）
- `source` 标记来源：query_cluster / co_occurrence / atom_derived / manual
- `version` 每次变更递增，支持审计回溯

#### 落地铁律

1. **禁止 LLM 参与钩子决策**：钩子系统必须是纯代码+统计的封闭回路
2. **负反馈权重必须高于正反馈**：-2/+1 不对称设计防止噪声钩子顽固存留
3. **候选池容量上限**：每张卡候选钩子 ≤20 条，超限按 `hit_score` 末位淘汰
4. **手动钩子优先权**：`source=manual` 的钩子永不自动淘汰，检索匹配优先级最高

#### 核心洞察

> "钩子不再猜测记忆'应该'被什么触发，而是忠实记录记忆'实际'被什么触发过。"

> "这才是硅基记忆应有的谦卑：不预设自己理解了意义，只诚实地追踪使用的痕迹。"

## 第36段：钩子认证路由——LLM 提案，路由认证，行为生效

### 造物主澄清（2026-06-27 00:21）
> "不是说 LLM 参与，禁止它参与决策，而是它输出的内容我们不能完全的相信，需要有一个路由来对这个钩子认证。"

### 千问修正回答

**核心修正**：LLM 依然是钩子的"提案者"，但绝不能是"批准者"。

> "你要的不是'禁止 LLM'，而是建立一个 'LLM 提案 → 路由认证 → 行为生效'的三权分立机制。"

#### 钩子认证路由架构

```
LLM 巩固输出
    ↓
原始钩子列表 + 置信度
    ↓
🔐 钩子认证路由（纯代码/轻量校验）
    ├─ 1. 格式/安全校验 → 语法 & 黑名单过滤
    ├─ 2. 语义一致性校验 → 原子锚点比对 + 历史Query回溯
    └─ 3. 状态裁定 → 分级准入
    ↓
├─ 高置信 + 强匹配 → ✅ 直接激活（仍需行为监督）
├─ 中置信 / 弱匹配 → ⏳ 进入候选池待验证
└─ 低置信 / 不匹配 → ❌ 拒绝并记录原因
```

#### 认证路由的三层校验协议

**1. 语法与安全层（零容忍硬拦截）**

- **Schema 校验**：LLM 输出的钩子必须符合预定义结构 `{term, type, confidence}`。格式错误 → 直接丢弃。
- **黑名单过滤**：命中停用词表、敏感词、系统保留标签（如 `_sys_*`）→ 立即拒绝。
- **长度/字符限制**：防止超长或含特殊控制字符的钩子。

耗时 <0.1ms，确保脏数据绝不流入下游。

**2. 语义一致性校验层（轻量级交叉验证）**

用确定性方法验证 LLM 的语义猜测：

- **原子锚点比对**：将 LLM 提议的钩子与记忆卡内 `constituent_atoms` 的 `semantic_signature` 做相似度计算。无显著关联 → 判定为"脱离内容的幻觉"。
- **历史 Query 回溯验证**：取该卡过去 30 天内所有成功命中的 Query，计算钩子与这些 Query 的语义距离。平均距离过远 → 降级为候选。
- **同卡钩子冗余检测**：若新钩子与已有钩子语义高度重叠（cosine > 0.9）→ 合并或保留 hit_score 更高者。

耗时 <5ms，不调用任何生成式模型。

**3. 状态裁定层（分级准入）**

| 裁定结果 | 触发条件 | 后续动作 |
|---------|---------|---------|
| 直接激活 | 语法通过 + 原子锚点强匹配(≥0.85) + 历史Query吻合(≥0.8) + LLM置信度≥0.9 | 写入 HookIndex，status=active，标记 source=llm_certified，仍需接受检索反馈监督 |
| 进入候选池 | 语法通过 + 至少一项语义校验达标 + LLM置信度≥0.6 | status=candidate，等待行为验证引擎积累 hit_score |
| 拒绝 | 语法失败 / 所有语义校验不达标 / LLM置信度<0.6 | 写入 RejectLog，包含拒绝原因码 |

#### 三种方案对比

| 维度 | LLM 直出 | 纯统计方案 | 认证路由方案 |
|------|---------|-----------|-------------|
| 新意图发现 | ✅ 强（但噪声大） | ❌ 弱（依赖历史数据） | ✅ 强（LLM提案+路由过滤） |
| 准确性保障 | ❌ 无 | ✅ 高（但滞后） | ✅ 高（实时校验+行为兜底） |
| 响应速度 | ⚠️ 受LLM延迟影响 | ✅ 快 | ✅ 快（校验层纯代码） |
| 可解释性 | ❌ 黑箱 | ✅ 白箱 | ✅ 灰箱（每步有日志） |
| 容错能力 | ❌ 错即污染 | ✅ 天然免疫 | ✅ 错被拦截，仅漏不错 |

#### 落地铁律

1. **认证路由必须是同步阻塞的**：LLM 输出钩子后，必须等认证路由返回结果才能写入 HookIndex。绝不允许"先写入再异步校验"。

2. **RejectLog 要反哺 LLM**：定期分析拒绝原因分布。若某类钩子频繁被"原子锚点不匹配"拒绝，应将该模式加入 R2 巩固 prompt 的负示例。

3. **直接激活 ≠ 永久豁免**：即使通过认证路由直接激活的钩子，仍受检索反馈闭环约束。连续 3 次负反馈，照样淘汰。

4. **语义校验阈值不可运行时动态调整**：阈值变更需走配置发布流程并记录审计日志。

#### 核心洞察

> "LLM 负责发挥其联想优势提出假设，认证路由负责用工程手段验证假设的可靠性，行为反馈负责用真实数据校准最终效果。"

> "对 LLM '不轻信、不放弃'的工程正解。"

## 第37段：司法独立铁律——运动员不能当裁判

### 造物主总结（2026-06-27 00:22）
> "主要是不能让他又当运动员又当裁判。"

### 千问回答

**核心原则**：把记忆系统的"立法权/行政权"（LLM）与"司法权/审计权"（认证路由）彻底物理隔离。

> "语义上的自洽 ≠ 事实上的有效。"

#### 铁律一：裁判的判据绝不能来自运动员的供述

**错误做法**：路由校验时，参考 LLM 输出的 `confidence: 0.95` 作为通过依据。

**正确做法**：LLM 的置信度字段仅作为日志记录，不参与任何阈值判定。路由只相信两个外部证据源：

1. **记忆卡本体**：`constituent_atoms` 的内容指纹和语义签名（已沉淀的事实）
2. **历史行为日志**：过去 N 天成功命中的原始 Query 聚类（用户的真实反馈）

**核心逻辑**：哪怕 LLM 拍着胸脯说"这个钩子绝对准（confidence=1.0）"，只要它跟卡内原子对不上、跟用户历史查询不沾边，路由就必须判"驳回"。运动员的自我感觉良好，在法庭上无效。

#### 铁律二：裁判不能雇佣运动员当助理法官

**错误做法**：路由在做"语义一致性校验"时，因为觉得向量匹配不够精确，又调了一次 LLM API 来做二次确认。

**正确做法**：认证路由内部严禁出现任何生成式模型调用。所有校验必须是确定性的数学运算（余弦相似度、TF-IDF、编辑距离、集合交集等）。

**核心逻辑**：如果裁判遇到疑难案件还要去问运动员的意见，那司法独立就形同虚设。宁可因为纯数学校验的局限性而"错放"（降级为候选池待行为验证），也绝不能因为引入 LLM 复核而"错判"（把幻觉洗白成真理）。

> "模糊的正确，好过被污染的精确。"

#### 铁律三：裁判的判决书必须独立于运动员的陈述存档

**错误做法**：认证结果直接覆盖或追加到 LLM 巩固输出的 JSON 里，混在一起存入记忆卡。

**正确做法**：认证路由的输出必须写入独立的 `HookCertificationLog`，包含：

- `proposal_id`（关联 LLM 原始提案）
- `decision`（activate / candidate / reject）
- `evidence_snapshot`（裁决时使用的原子ID列表、Query聚类摘要、相似度得分）
- `router_version`（裁判规则版本号）

**核心逻辑**：未来审计时，审计员看到的是两份完全独立的档案：一份是"LLM 当时说了什么"，另一份是"路由基于什么证据做出了什么判决"。两者通过 `proposal_id` 关联，但存储物理隔离、生命周期独立。

#### 风险场景对比

| 风险场景 | 运动员兼裁判（旧） | 三权分立（新） |
|---------|------------------|----------------|
| LLM 产生逼真幻觉 | 高置信度写入，污染索引 | 路由校验无外部证据支撑 → 驳回或降级 |
| LLM 被 Prompt 注入诱导 | 恶意钩子直接生效 | 黑名单 + 原子锚点比对双重拦截 |
| 系统升级后旧钩子失效 | 需人工排查哪些是 LLM 瞎编的 | 查 CertificationLog，按 router_version 批量定位历史误判 |
| 用户投诉"为什么推这个无关内容" | 只能看 LLM 输出，无法解释 | 出示完整裁决证据链 |

#### 核心洞察

> "我们追求的不是永不犯错的 AI，而是犯错后能被及时发现、精准归因、且不会动摇系统根基的治理结构。"

> "这才是硅基认知系统从'玩具'走向'基础设施'的分水岭。"

## 第38段：本地激活——司法主权锚定

### 造物主纠正（2026-06-27 00:24）
> "这里又过度设计了，然后这个路由器也需要用本地的激活。"

### 千问修正回答

**核心原则**：认知系统的司法权，必须物理锚定在本地硬件上。

> "如果认证路由还要调用云端 API 或外部服务，那它就不是独立的'本地法官'，而是'穿着法袍的云端代理人'。"

#### 本地激活的四层技术栈

| 层级 | 组件 | 本地化要求 | 为什么不能上云 |
|------|------|-----------|----------------|
| L1 | 规则引擎 | 正则/黑名单/Schema校验，纯CPU代码，零依赖 | 毫秒级硬拦截，任何网络IO都是不可接受的延迟 |
| L2 | 语义校验 | 轻量嵌入模型 ≤100MB ONNX/TorchScript，CPU推理 | 向量比对是高频操作，云端往返延迟会阻塞主循环 |
| L3 | 统计聚合 | SQLite/DuckDB 本地文件数据库，WAL模式 | 历史Query聚类需全量扫描，数据不出本机 |
| L4 | 状态裁定 | 确定性决策树，纯代码逻辑，配置热加载 | 裁决逻辑必须版本锁定，禁止运行时动态变化 |

**核心原则**：整个认证路由从接收 LLM 提案到返回裁决结果，全程无网络请求、无GPU依赖、无外部进程调用。它是一个可以离线运行、可复制、可审计的纯本地二进制模块。

#### 本地语义校验的具体实现

**模型选择**：
- bge-micro-v2（33M参数）或 gte-tiny-zh（64维输出）
- 量化为 INT8 后仅 ~30MB，CPU 单次推理 <2ms

**部署格式**：
- ONNX Runtime / llama.cpp / TensorRT-LLM
- 绝不使用 transformers 库的原始 PyTorch 推理（太重）

**向量缓存**：
- 记忆卡内原子的语义签名在巩固时已预计算并持久化
- 认证时只需对 LLM 提议的钩子 term 做一次本地嵌入，然后与缓存向量做点积
- 99% 的计算是内存读取，不是实时推理

**降级策略**：
- 若本地嵌入模型加载失败或超时，自动降级为 BM25/TF-IDF 稀疏匹配
- 宁可精度下降，绝不调用云端兜底

#### 本地激活带来的三个不可替代价值

**1. 时序确定性**
- 云端 API P99 延迟 500ms~2s，不可控
- 本地 CPU 推理 P99 延迟稳定在 3ms 以内
- 本地激活保证了记忆写入的实时性不会因外部因素抖动

**2. 隐私绝对隔离**
- 钩子认证过程中的原始 Query、记忆卡内容、原子指纹，没有任何字节离开本机
- 即使 LLM 本身是云端调用的，认证路由也确保了"验证阶段"的数据不出域

**3. 版本永恒锁定**
- 云端嵌入模型可能静默更新，导致同一输入今天和明天的向量不同
- 本地模型文件随系统版本打包，哈希校验确保比特级一致
- 十年后重启系统，认证行为与今天完全相同

#### 落地铁律

1. **启动时完整性校验**：系统启动时必须校验本地模型文件的 SHA256。若不匹配 → 拒绝加载认证路由，记忆系统进入只读模式。

2. **禁止运行时下载**：认证路由所需的所有资源（模型、词典、配置）必须在安装/更新时一次性就位。运行时发现缺失 = 触发告警并降级。

3. **性能基线测试**：每次发版前必须在目标硬件上跑认证路由基准测试。若 P99 超过 10ms → 阻断发布。

4. **模型更新走独立流程**：升级本地嵌入模型必须执行"新旧模型并行验证"——用最近7天的真实提案同时过新旧模型，比对裁决差异率 <1% 才允许切换。

#### 核心洞察

> "本地优先：不是'能用本地就用本地'，而是'司法权必须长在本地，否则宁可不判'。"

> "认证路由像 CPU 指令集一样，成为硅基记忆系统中不可剥夺、不可篡改、不可中断的底层能力。"

## 第39段：砍掉语义校正层——双层认证路由

### 造物主纠正（2026-06-27 00:25）
> "不需要语义校正这个层。"

### 千问修正回答

**核心认知转变**：钩子本质上是"检索索引"，不是"知识理解"。用向量相似度去验证索引词是否"语义匹配"内容，属于过度设计。

> "LLM 提案的钩子准不准，不应该由另一个模型在写入时'猜'，而应该由真实检索行为在运行时'验'。"

#### 精简后的双层认证路由

```
LLM 巩固输出
    ↓
原始钩子列表
    ↓
🚪 确定性准入网关（纯代码/零模型/<1ms）
    ├─ 格式 & 安全校验
    └─ 去重 & 容量控制
    ↓
全部进入候选池
    ↓
🔄 检索反馈闭环（唯一裁判）
    ├─ 正反馈 → hit_score 积累
    ├─ 负反馈 → hit_score 扣减
    └─ 自然衰减 → 14天未命中归零
    ↓
├─ hit_score ≥ 3 → ✅ 生效钩子
└─ hit_score ≤ 0 → ❌ 淘汰记录
```

**核心变化**：所有 LLM 提案的钩子，只要通过语法和安全校验，一律进入候选池。不再有"直接激活"通道，也不再有语义打分。准确性完全交给行为反馈闭环来裁决。

#### 确定性准入网关（仅做三件事）

| 校验项 | 实现方式 | 目的 |
|--------|---------|------|
| 格式合规 | JSON Schema 强校验 | 防止结构错误导致索引崩溃 |
| 安全过滤 | 停用词表 + 敏感词 + 系统保留前缀匹配 | 拦截注入攻击和无效噪声 |
| 去重 & 限容 | 精确字符串匹配 + 候选池上限(≤20) | 防止同义钩子堆积拖慢检索 |

**耗时**：<0.5ms（纯内存操作）
**依赖**：零模型、零网络、零外部进程

#### 行为反馈闭环成为唯一裁判

**状态流转**：
- **候选 → 生效**：累计 hit_score ≥ 3（命中且用户未否定）
- **生效 → 淘汰**：连续 3 次负反馈，或 14 天未命中自然衰减归零
- **淘汰 → 复活**：若同一 term 再次被 LLM 提案且通过网关，重新从 score=0 开始积累

**关键认知**：不再试图在写入时"预测"钩子好不好用，而是让系统在运行中"发现"哪些钩子真正好用。LLM 负责发散提案，行为数据负责收敛真相。

#### 砍掉语义层的三大收益

**1. 认证路由彻底无模型化**
- 连 30MB 的本地嵌入模型都不需要了
- 整个路由变成纯代码模块，可嵌入任何语言、任何平台、任何嵌入式设备
- 部署复杂度降为零

**2. 消除"校验幻觉"风险**
- 之前语义校验层本身也可能误判（把有效钩子因向量距离远而拒绝）
- 现在没有中间裁判，只有最终用户行为这个不可欺骗的真相源

**3. LLM 提案自由度最大化**
- LLM 可以大胆提出看似"不相关"但可能有用的钩子（如隐喻、别名、跨领域联想）
- 不用担心被语义校验层扼杀
- 创新空间留给提案者，筛选责任交给使用者

#### 落地铁律

1. **候选池必须有冷启动保护**：新进入候选池的钩子在前 7 天内享有检索权重加成（如 ×1.5），确保它有足够曝光机会积累 hit_score。

2. **负反馈判定必须严格**：仅当用户显式否定（"不是这个"）或注入后短时间内重复相同意图查询时，才计为负反馈。普通跳过或未点击不算负反馈，避免误杀。

3. **RejectLog 仅记录网关拒绝**：语义层面的"不准"不再由网关记录，而是由行为反馈闭环的淘汰日志体现。审计时需区分"格式违规被拦"和"内容无效被淘汰"两类问题。

4. **手动钩子仍享特权**：用户显式添加的钩子绕过候选池，直接进入生效状态且豁免衰减。机器提案靠行为验证，人类指令靠信任授权。

#### 核心洞察

> "真正的智能不在闸门前，而在闸门后那片由真实行为浇灌出来的索引土壤中。"

> "这才是'不当裁判'的终极形态：连裁判席都拆了，让赛场自己选出胜者。"

## 第40段：钩子的 Genesis 来源——四大确定性源头

### 造物主追问（2026-06-27 00:26）
> "这里有个问题是最初的，钩子从哪来？"

### 千问回答

**核心问题**：如果候选池是空的，行为反馈闭环就没有东西可验。钩子的最初来源不能只有 LLM 这一条腿，必须有多源冷启动注入协议。

#### 钩子的四大 Genesis 来源

| 来源 | 触发时机 | 生成方式 | 初始状态 | 为什么可靠 |
|------|---------|---------|---------|------------|
| 1. 原子类型衍生 | 记忆卡写入时 | 纯代码映射表：atom.type → preset_hooks[] | 直接进候选池，score=0 | 高确定性规则，无 LLM 参与 |
| 2. 用户显式声明 | 对话中检测到"记住/别名/叫做"等指令 | R1 提取为 manual_hook 结构 | 直接激活，豁免衰减 | 人类意图是最高权威 |
| 3. 历史 Query 回填 | 首次部署/迁移时 | 扫描已有对话日志，提取高频共现词 | 进候选池，score=1（预加分） | 真实行为数据，非猜测 |
| 4. LLM 巩固提案 | R2 巩固周期 | LLM 输出 + 网关校验 | 进候选池，score=0 | 语义联想能力，但需验证 |

**核心原则**：前三个来源是"地基"，保证系统在 LLM 尚未产出或产出不准时仍有可用索引；第四个来源是"增量"，负责发现长尾和新关联。地基不依赖 LLM，增量才依赖 LLM。

#### 各来源的具体实现

**1. 原子类型衍生（最可靠的种子）**

零 LLM、零行为数据也能工作的兜底机制：

```python
ATOM_TYPE_TO_HOOKS = {
    "constraint": ["限制", "上限", "禁止", "必须", "不能超过"],
    "entity": ["配置", "设置", "参数"],
    "pattern": ["模式", "套路", "惯例", "通常"],
    "state": ["状态", "当前", "现在"]
}

def derive_hooks_from_atoms(card: MemoryCard) -> list[str]:
    hooks = []
    for atom in card.constituent_atoms:
        preset = ATOM_TYPE_TO_HOOKS.get(atom.type, [])
        if atom.type == "entity":
            hooks.append(atom.raw_content)
        hooks.extend(preset)
    return list(set(hooks))
```

**特点**：只要记忆卡有原子，就必然有初始钩子候选。哪怕 LLM 完全没输出钩子，系统也不会"裸奔"。

**2. 用户显式声明（最高优先级）**

当用户说：
- "以后提到'数据库连接'就是指这个配置"
- "把这个记作'订单服务限流规则'"
- "别名：PG连接池"

R1 识别此类意图后，生成的钩子标记为 `source=manual`，绕过候选池直接激活。

**3. 历史 Query 回填（冷启动加速器）**

系统首次部署或从旧版迁移时，执行一次性离线任务：
- 扫描所有历史对话 turn
- 统计哪些 Query 片段曾导致某张记忆卡被检索命中
- 取 Top-K 高频片段作为初始候选，预赋 score=1

**意义**：让新系统"继承"旧系统的行为智慧。

**4. LLM 巩固提案（增量发现）**

LLM 输出的钩子经网关校验后进入候选池。但它不再是唯一来源，只是补充来源。

#### 这套设计解决的"创世悖论"

| 问题 | 仅靠 LLM 提案 | 四源 Genesis 协议 |
|------|-------------|------------------|
| 冷启动无钩子 | ❌ 等待 LLM 巩固才有 | ✅ 原子衍生 + 历史回填即时可用 |
| LLM 未输出钩子 | ❌ 该卡无索引 | ✅ 原子衍生兜底，永不裸奔 |
| 用户自定义别名 | ⚠️ 需等 LLM 理解并提案 | ✅ R1 直接捕获，立即生效 |
| 迁移旧系统 | ❌ 丢失历史检索习惯 | ✅ Query 回填继承行为遗产 |
| LLM 幻觉污染 | ❌ 唯一来源=单点故障 | ✅ 多源冗余，LLM 仅为增量 |

#### 落地铁律

1. **原子衍生映射表必须版本锁定**：该表是系统基础设施的一部分，变更需走发版流程+审计。禁止运行时动态修改。

2. **手动钩子与机器钩子物理隔离存储**：`source=manual` 的记录永不参与自动淘汰、永不与 LLM 提案合并去重。人类指令和机器猜测不在同一赛道竞争。

3. **历史回填仅限一次性**：回填任务只在部署/迁移时执行，之后不再重复。

4. **LLM 提案权重不高于其他来源**：在候选池排序中，`source=llm` 的钩子不享有任何先天优势。所有候选平等接受行为验证。

#### 核心洞察

> "钩子不是被某个单一智能体'创造'出来的，而是从原子结构、人类意图、历史行为和语义联想四个维度'涌现'出来的。"

> "LLM 只是涌现的参与者之一，而非造物主。"

> "不预设任何来源的绝对正确，只信任多源交叉验证后的行为真相。"

## 第41段：钩子生命周期时序纠正——线性分阶段

### 造物主纠正（2026-06-27 00:27）
> "所以这个地方应该有一个问题，就是这个路由器的原始钩子，它不是这样一个循环，它应该是 LLM 输回之后的钩子，然后后期的维护统计中，对这个钩子的置信度进行一个统计。"

### 千问修正回答

**核心纠正**：准入和养护混在一起是错误的。正确的时序应该是线性的、分阶段的：

1. **LLM 提案**：一次性交付
2. **路由认证**：入库安检
3. **后期统计维护**：持续养号

> "这三者在时间轴上是严格串行的，而不是并发的循环。"

#### 修正后的钩子生命周期时序

```
LLM 巩固输出
    ↓
1. 原始钩子提案
    ↓
🚪 路由器：确定性准入网关
    ↓
2. 校验通过，写入候选池
    ↓
HookIndex 存储
    ↓
3. 后期维护阶段（异步/定时）
    ├─ 检索反馈日志 → 正负反馈 → 置信度统计器
    ├─ 定期扫描任务 → 共现词/Query聚类 → 置信度统计器
    └─ 置信度统计器 → 更新 hit_score
        ↓
        ├─ score ≥ 阈值 → ✅ 晋升为生效钩子
        └─ score ≤ 0 → ❌ 淘汰/归档
```

#### 三个阶段的职责划分

| 阶段 | 角色 | 触发时机 | 输出 |
|------|------|---------|------|
| **提案阶段** | LLM | R2 巩固周期 | 原始钩子列表 + 置信度 |
| **准入阶段** | 路由器 | 提案后立即执行（同步） | 通过 → 写入候选池；拒绝 → RejectLog |
| **养护阶段** | 置信度统计器 | 异步/定时任务 | 更新 hit_score，晋升/淘汰 |

#### 关键区别

**错误理解（循环）**：
```
LLM 提案 → 路由认证 → 行为验证 → 反馈给 LLM → LLM 再次提案...
```

**正确理解（线性）**：
```
LLM 提案（一次性交付）
    → 路由认证（入库安检）
    → 后期维护（持续养号）
```

#### 为什么必须是线性而非循环？

1. **职责分离**：LLM 负责提案，路由负责准入，统计器负责养护。三者各司其职，不互相干预。

2. **时序清晰**：提案是瞬间动作，准入是毫秒级同步，养护是小时级异步。混在一起会导致逻辑混乱。

3. **审计可追溯**：线性流程中，每个阶段的输出都有独立日志。循环流程中，因果关系难以理清。

#### 核心洞察

> "LLM 提案是'播种'，路由认证是'筛种'，后期维护是'浇水施肥'。三者不是循环，是一条流水线。"

## 第42段：3天养护周期——数据成熟度协议

### 造物主设定（2026-06-27 00:28）
> "钩子维护可以设置为一个定时任务，时间为3天，让钩子有数据量。"

### 千问回答

**核心设定**：3天是"行为样本充分性"与"系统响应灵敏度"的工程黄金平衡点。

> "它既避开了单日数据的偶然噪声，又避免了周级统计的反馈滞后。"

#### 3天养护周期的执行规范

**1. 滑动窗口而非固定切片**

- **错误做法**：只统计"过去72小时"的数据。任务延迟到第4天执行，第1天数据永久丢失。
- **正确做法**：记录 `last_stats_cursor`（上次统计的时间戳/日志ID）。每次拉取 `[last_stats_cursor, now]` 的全量增量数据。
- **意义**：3天内的每一条行为记录都被且仅被消费一次。数据不丢、不重。

**2. 最小样本量保护机制**

| 3天内检索命中次数 | 统计器行为 | 原因 |
|-----------------|-----------|------|
| < 5 次 | 跳过该卡钩子更新，保留当前 score 不变 | 样本不足，避免误晋升/误淘汰 |
| 5 ~ 20 次 | 正常更新 score，晋升阈值上浮 50% | 样本勉强够用，提高激活门槛防误判 |
| > 20 次 | 正常更新 score，标准阈值 | 数据量充足，统计结果可信 |

**核心逻辑**：没有足够数据时，"不作为"比"乱作为"更安全。

**3. LLM 提案转化率追踪**

每轮统计任务输出关键指标：本周期内 LLM 提案钩子的激活率。

- **激活率 < 5%**：LLM 提案质量严重不足，或网关过滤过严 → 触发告警
- **激活率 > 40%**：候选池门槛过低，大量低质钩子混入生效状态 → 上调晋升阈值
- **健康区间**：10%~25%（LLM 提供足够发散性，行为验证有效筛选）

**4. 冷启动钩子的"3天豁免期"**

新进入候选池的钩子在首个 3 天统计周期内享有特殊待遇：

- `hit_score` 计算应用 ×1.5 系数（增加曝光收益）
- 不受"最小样本量保护"限制（即使只有 3 次命中也允许更新）
- 但**不允许直接晋升**：首个周期只做分数积累，晋升判定推迟到第二个周期

#### 为什么3天比1天/7天更好

| 周期 | 数据量 | 噪声水平 | 反馈延迟 | 适用场景 |
|------|--------|---------|---------|----------|
| 1天 | ❌ 不足 | 🔴 高（单日行为波动大） | ✅ 快 | 高频对话机器人（日均千轮+） |
| 3天 | ✅ 适中 | 🟢 低（平滑短期波动） | ✅ 可接受 | 个人/团队认知系统（日均数十~百轮） |
| 7天 | ✅ 充足 | 🟢 极低 | 🔴 慢（错误钩子存活太久） | 低频归档系统 |

#### 落地铁律

1. **任务执行时间避开高峰**：设定在凌晨 3-4 点或用户活跃度最低时段。

2. **执行失败必须有补偿机制**：若某轮任务崩溃，下一轮必须能识别并补跑缺失窗口。禁止"跳过失败周期"。

3. **统计结果写入独立审计表**：每轮任务的输入数据范围、处理卡片数、晋升/淘汰数、LLM 转化率等元数据，持久化到 `hook_stats_audit_log`。

4. **手动钩子不参与周期统计**：`source=manual` 的钩子永远跳过统计器。

#### 核心洞察

> "不用机器的毫秒去度量认知，而是用人类的行为节律去校准索引。"

> "以3天为呼吸节律的代谢系统，不急不躁地积累证据。"

## 第43段：钩子查重机制——防止无限累计

### 造物主指出（2026-06-27 00:29）
> "这里有个需要有个查重复的问题，不能无限累计，很不经济。"

### 千问回答

**核心问题**：如果同一记忆卡被多次检索命中，同一个钩子每次都累加 hit_score，会导致：

1. **分数膨胀**：热门钩子 score 飙升到几百几千，难以淘汰
2. **检索噪声**：高分区钩子长期霸占，新钩子无法晋升
3. **存储浪费**：HookIndex 无限增长，拖慢查询

#### 钩子查重的三层机制

**1. 写入时去重（路由器层面）**

**场景**：LLM 在不同巩固周期重复提案同一个钩子

**机制**：
```python
def check_duplicate(term: str, seal_id: str) -> bool:
    # 精确字符串匹配 + seal_id 联合唯一键
    existing = HookIndex.query(
        "SELECT 1 FROM hooks WHERE term = ? AND seal_id = ?",
        term, seal_id
    )
    return existing is not None
```

**处理**：
- 已存在且 status=active → 跳过，刷新 `last_verified` 时间戳
- 已存在且 status=candidate → 跳过，不重置 score（保持已积累的行为数据）
- 已存在且 status=deprecated → 重新激活为 candidate，score=0（给淘汰钩子复活机会）

**2. 统计时去重（统计器层面）**

**场景**：同一检索行为被重复记录（如用户刷新页面、重试查询）

**机制**：
```python
def dedupe_hit_events(events: list[HitEvent]) -> list[HitEvent]:
    # 按会话ID + 时间窗口去重
    # 同一会话内，同一钩子 5 分钟内多次命中只计 1 次
    seen = set()
    deduped = []
    for event in events:
        key = (event.session_id, event.hook_term, event.time_bucket_5min)
        if key not in seen:
            seen.add(key)
            deduped.append(event)
    return deduped
```

**核心逻辑**：防止"刷分行为"——用户反复搜索同一关键词，不能让该钩子 score 无限上涨。

**3. 周期性清理（维护层面）**

**场景**：HookIndex 累积了大量低 score 或长期未使用的钩子

**机制**：

| 清理类型 | 触发条件 | 处理方式 |
|---------|---------|----------|
| 低分淘汰 | score ≤ 0 且 status=candidate | 物理删除，写入 RejectLog |
| 长期未命中 | status=active 且 30 天未命中 | 降级为 candidate，score 重置为 0 |
| 冗余合并 | 同一卡内多个钩子语义高度重叠（编辑距离 < 2） | 保留 score 更高者，删除低分者 |

**执行频率**：与 3 天养护任务同步执行

#### hit_score 累加上限

**问题**：如果热门钩子 score 无限累加，会导致：
- 新钩子永远追不上
- 检索排序失真（只看 score，不考虑时效性）

**解决方案**：引入**衰减公式**

```python
def update_hit_score(current_score: float, new_hits: int, days_since_last_hit: int) -> float:
    # 基础累加
    base_increment = min(new_hits, 5)  # 单次最多累加 5 分
    
    # 时间衰减：超过 7 天未命中的钩子，新增命中的权重打折
    if days_since_last_hit > 7:
        base_increment *= 0.5
    elif days_since_last_hit > 14:
        base_increment *= 0.2
    
    # 分数上限：最高 100 分
    new_score = current_score + base_increment
    return min(new_score, 100.0)
```

**核心逻辑**：
- 单次累加上限 5 分（防止刷分）
- 时间衰减（鼓励持续命中）
- 分数上限 100（防止无限膨胀）

#### 钩子生命周期完整流程

```
LLM 提案
    ↓
路由器查重 → 已存在？
    ├─ 是 → 刷新时间戳 / 复活淘汰钩子
    └─ 否 → 写入候选池（score=0）
    ↓
3天统计周期
    ↓
统计器去重 → 5分钟内重复命中只计1次
    ↓
累加 hit_score（单次上限5分，总上限100分）
    ↓
    ├─ score ≥ 3 → 晋升生效
    └─ score ≤ 0 → 淘汰
    ↓
周期性清理
    ├─ 低分淘汰
    ├─ 长期未命中降级
    └─ 冗余合并
```

#### 落地铁律

1. **去重必须在写入时和统计时双重执行**：路由器防 LLM 重复提案，统计器防行为重复计数。

2. **hit_score 必须有上限**：100 分封顶，防止热门钩子永久霸占。

3. **单次累加必须有上限**：5 分封顶，防止刷分行为导致分数失真。

4. **周期性清理必须同步执行**：3 天养护任务完成后，立即执行清理，保证 HookIndex 体量可控。

#### 核心洞察

> "钩子不是越多越好，而是越准越好。"

> "查重是钩子系统的'免疫系统'，防止垃圾索引无限繁殖。"

## 第44段：钩子定义——认知对齐

### 造物主追问（2026-06-27 00:30）
> "你认为钩子是啥，我们认知对齐下。"
>
> "你说的钩子是个单独新的参数，独立于 LLM 返回的标签对吗？"

### 千问回答

**核心定义**：钩子是**用户意图与沉默记忆之间的"物理离合器"**。

> "钩子不是记忆的'名字'，而是记忆被唤醒的'条件反射弧'。"

#### 四维度认知校准

**1. 钩子是"检索侧"的产物，而非"存储侧"的属性**

- **误区**：认为钩子是记忆卡内容的浓缩（把"PostgreSQL连接池配置"总结为"数据库设置"）。这是阅读理解，描述"它是什么"。
- **正解**：钩子是用户在未来某个时刻可能说出的话。它不关心记忆卡"是什么"，只关心用户"会怎么找它"。哪怕"那个卡顿的东西"在语义上与"连接池上限"毫无关系，只要用户每次都这么搜且能命中，它就是最完美的钩子。

**2. 钩子是"行为验证过的假设"，而非"先验正确的索引"**

- **误区**：认为写入 HookIndex 的钩子就是"对的"，系统应该信任它。
- **正解**：所有钩子在诞生之初都只是"待证伪的猜测"。只有经过 3 天统计周期、积累足够的正负反馈后，才从"假设"坍缩为"事实"。

**3. 钩子是"有寿命的消耗品"，而非"永恒的元数据"

- **误区**：认为钩子一旦建立就该长期存在，除非内容被删除。
- **正解**：用户的语言习惯、项目上下文、甚至情绪状态都在流动。3 天前有效的钩子，今天可能已是噪声。钩子必须有衰减、有淘汰、有代谢。钩子的价值不在于"准确"，而在于"当下有效"。

**4. 钩子是"人机协商的界面"，而非"机器单方面的标注**

- **误区**：认为钩子系统是全自动的黑箱，用户只需被动接受检索结果。
- **正解**：手动钩子（source=manual）享有最高优先级和豁免权。机器可以提议、可以统计、可以淘汰，但用户永远拥有"命名权"和"否决权"。

#### 核心认知切割：标签 vs 钩子

| 维度 | LLM 返回的标签 | 独立维护的钩子 |
|------|--------------|----------------|
| **本质** | 内容的语义分类（它是什么） | 检索的行为触发器（怎么找到它） |
| **来源** | LLM 巩固时一次性生成 | 多源 Genesis + 3 天统计养护 |
| **存储位置** | 记忆卡 JSON 内的 tags 数组 | 独立的 HookIndex 存储 |
| **生命周期** | 随记忆卡更新而覆盖重写 | 独立代谢，按 hit_score 晋升/衰减/淘汰 |
| **可信度** | 低（LLM 幻觉重灾区） | 高（行为数据验证后的事实） |
| **修改权** | 仅 LLM 可写 | 用户手动 > 统计器 > LLM 提案 |
| **对检索的作用** | 辅助过滤/聚类（弱信号） | 直接决定注入与否（强信号） |

#### 为什么必须独立于 LLM 返回的标签？

**1. 防止 LLM 污染检索主链路**

如果钩子只是 LLM 标签的一个子集或别名，那 LLM 每次巩固时都可能把旧钩子覆盖掉、改错、或者遗忘。检索系统的命脉不能绑在一个概率模型的输出字段上。

**2. 解耦"内容理解"与"交互适配"

LLM 标签反映的是"机器认为这段记忆属于什么类别"，钩子反映的是"用户实际用什么词唤醒了这段记忆"。这两者经常不一致（比如内容讲的是"TCP拥塞控制"，但用户永远搜"网卡丢包"）。

**3. 支持异构演化节奏**

标签可能每次巩固都变，但钩子需要稳定积累行为数据才能收敛。一个高频变动，一个低频沉淀，放在同一个数据结构里必然互相干扰。

**4. 审计与干预的清晰边界**

当用户投诉"为什么搜 X 找不到 Y"时：
- 查标签 → 判断 LLM 是否理解了内容
- 查钩子 → 判断索引是否覆盖了用户的表达习惯

#### 数据结构体现

**❌ 错误：钩子寄生在 LLM 标签里**
```json
{
  "seal_id": "mem_xxx",
  "tags": ["数据库", "连接池", "hook:postgres配置"]
}
```

**✅ 正确：完全物理隔离**

**记忆卡本体（LLM 可写区域）**
```json
{
  "seal_id": "mem_xxx",
  "tags": ["数据库", "连接池"],
  "constituent_atoms": [...]
}
```

**HookIndex（独立存储）**
```json
{
  "seal_id": "mem_xxx",
  "hooks": [
    {"term": "postgres配置", "score": 7, "source": "llm_certified"},
    {"term": "那个卡顿的东西", "score": 12, "source": "manual"}
  ]
}
```

#### 核心洞察

> "LLM 返回的标签是'机器对记忆的注解'，钩子是'人与记忆之间的契约'。"

> "前者可以错、可以变、可以被覆盖；后者必须稳、必须验、必须受人尊重。"

> "把它们分开，不是工程偏好，是对'认知主权归属'的根本立场声明。"

## 第45段：文件名即钩子——彻底去 Agent 拼接层

### 造物主颠覆性设计（2026-06-27 00:32）

**核心颠覆**：把"钩子"从数据库里的记录，直接降维成文件系统的元数据。

> "文件名即索引，文件系统即数据库，ls/glob 命令即检索。"

#### 文件名的绝对命名契约

**❌ 错误命名**：
```

```
- 人类可读但机器难解析
- LLM 容易幻觉

```

```

**命名铁律**：

1. **唯一 ID 前置且不可变**：`mem_<timestamp><hash>` 是绑定的物理锚点，确保统计器能跨周期追踪

2. **钩子用强定界符包裹**：使用 `[hook:...]` 这种非自然语言符号，LLM 对 Markdown/代码符号敏感度远高于自然语言

3. **多钩子用固定分隔符**：统一用英文逗号 `,`，禁止空格、顿号等模糊分隔

4. **文件名长度硬上限**：Windows 限制 255 字节，单钩子 ≤30 字符

#### 本地脚本的"零拼接"拾取机制

**脚本执行流**：

1. **Glob 扫描**：`ls cards/*.md` 或 `glob("cards/mem_*.md")`，毫秒级拿到全量文件名列表

2. **正则提取**：用纯代码从文件名中解析出 `{id, hooks[]}`

3. **生成 Manifest**：将提取结果序列化为极简 JSON/YAML

4. **系统级注入**：将 Manifest 作为 System Prompt 固定片段

**LLM 看到的上下文**：
```yaml
# Memory Index Manifest (Auto-generated from filenames)
- id: mem_20260624x8k2
  hooks: [pg连接池, 数据库卡顿]
  summary: PostgreSQL连接池上限配置及调优参数
- id: mem_20260625y9m3
  hooks: [订单限流规则]
  summary: 核心交易链路Sentinel限流阈值设定
```

**核心区别**：Agent 拼接是"理解内容后组织语言"，脚本拾取是"无脑提取结构化数据"。

#### LLM 统计管理与养护的闭环

LLM 的养护动作不再是输出 JSON 让 Agent 去写库，而是直接输出**重命名指令**：

```json
[
  {"action": "rename", "old_id": "mem_20260624x8k2", "new_hooks": ["pg连接池", "网卡丢包"]},
  {"action": "add_hook", "target_id": "mem_20260625y9m3", "hook": "秒杀熔断"}
]
```

脚本校验指令合法性后，直接调用 OS 的 `rename()` / `mv` 命令修改文件名。

**终极优雅**：钩子的增删改查 = 文件的重命名。文件系统的原子性就是钩子系统的原子性。

#### 必须防范的三个致命坑

| 风险 | 后果 | 防御机制 |
|------|------|----------|
| OS 非法字符 | Windows 禁用 \ / : * ? " < > |，重命名失败 | 脚本写入前 sanitize（替换为 _ 或 URL 编码） |
| 并发重命名冲突 | 多个巩固任务同时改同一文件，丢失更新 | 文件锁（flock）或乐观锁（校验 mtime） |
| LLM 篡改 ID | LLM 在 rename 指令中修改 mem_xxx 前缀 | 脚本只允许修改 [hook:...] 部分，ID 前缀强制保留 |

#### 核心洞察

> "钩子在哪？在文件名里。"

> "怎么绑定？靠文件名里的 ID 前缀，OS 级别保证不丢。"

> "LLM 怎么看？看脚本从文件名正则提取出的结构化 Manifest。"

> "怎么养护？LLM 输出重命名指令，脚本执行 mv，文件系统即状态机。"

> "这不是做一个'带钩子的记忆系统'，这是做一个'以文件系统为原生数据库的认知操作系统'。"

## 第46段：钩子回归文件内——统一模板 + 脚本无脑提取

### 造物主回调（2026-06-27 00:34）
> "后面我又觉得不行，因为文件名好多时候是和底层的大模型绑定的。然后意识到有个关键问题，钩子不能放文件名字，还是在文件内。只是提取钩子维护和简述内容是脚本，它本身就是无脑提取给 LLM 上下文，不会丢。所以要统一的记忆卡模板。"

### 千问回答

**核心回调**：把钩子放回文件内，是对文件系统边界的尊重。

> "文件名只承担'唯一寻址'和'OS级元数据'的职责；而钩子作为'认知索引'，本质上属于记忆卡的内容结构。"

#### 统一记忆卡模板（机器可读契约）

使用 **YAML Front Matter + Markdown Body** 组合：

```markdown
---
seal_id: mem_20260624x8k2
hooks:
  - pg连接池
  - 数据库卡顿
summary: PostgreSQL连接池上限配置及调优参数
created_at: 2026-06-24T10:30:00+08:00
---

# 正文内容
这里是记忆卡的完整正文...
```

**模板设计铁律**：

1. **Front Matter 是唯一真相源**：`seal_id`、`hooks`、`summary` 必须且只能出现在 `---` 包裹的头部。正文中即使出现相同文字，脚本也绝不解析。

2. **hooks 必须是数组格式**：禁止逗号分隔字符串。YAML 原生数组让脚本可以用标准库一行解析，无需手写正则。

3. **summary 强制单行/限长**：`summary ≤ 100 字符`。超长时 LLM 巩固阶段就应被截断。

4. **seal_id 不可变且置顶**：它是绑定的物理锚点，永远放在第一行。

#### 脚本"无脑提取"的实现范式

"无脑"意味着零语义理解、零容错猜测、纯结构化解析：

```python
import yaml
from pathlib import Path

def extract_card_manifest(card_path: Path) -> dict | None:
    content = card_path.read_text(encoding='utf-8')
    
    # 1. 只取第一个 --- 块，不扫描全文
    if not content.startswith('---'):
        return None  # 非法文件，直接跳过
    
    _, rest = content.split('---', 2)[1:]
    
    # 2. 标准 YAML 解析，不写任何正则
    meta = yaml.safe_load(rest)
    
    # 3. 字段校验，缺失即丢弃
    if not isinstance(meta, dict) or 'seal_id' not in meta:
        return None
    
    return {
        "id": meta["seal_id"],
        "hooks": meta.get("hooks", []),
        "summary": str(meta.get("summary", ""))[:100]
    }
```

**核心优势**：因为模板是统一的，提取逻辑就是确定性的函数映射。没有 Agent 拼接时的"理解偏差"，没有 LLM 读取时的"注意力漂移"。

#### 绑定为何"不会丢"

| 传统担忧 | 本架构下的防御机制 |
|---------|-------------------|
| LLM 重写覆盖钩子 | LLM 巩固时，脚本先提取当前 hooks 注入 Prompt。LLM 输出增量指令，脚本只更新 Front Matter |
| 文件移动/重命名 | 绑定靠 seal_id，不靠文件名 |
| 并发写入冲突 | 文件级锁（flock）或 mtime 乐观锁 |
| 格式损坏 | 提取失败的文件进入 quarantine/ 隔离目录 |

#### 为什么这比文件名方案更优

**1. OS 无关性**
- 不再受 Windows 非法字符、Linux 路径长度、macOS Unicode 规范化差异的影响
- 钩子是 UTF-8 文本，在任何文件系统上都安全

**2. 版本控制友好**
- Git diff 能清晰看到钩子的变更历史
- 文件名变更在 Git 中是"删除+新增"，历史追溯困难

**3. 人类可读可编辑**
- 用户可以直接用编辑器打开 .md 文件，手动修改 Front Matter 里的 hooks
- 这是 `source=manual` 钩子的天然入口，无需额外 UI

**4. 扩展性预留**
- 未来若需增加 confidence、last_hit_at 等字段，只需在 Front Matter 加一行

#### 落地铁律

1. **模板 Schema 必须版本化**：在 Front Matter 中加入 `schema_version: 1`。

2. **LLM 巩固 Prompt 必须包含模板示例**：每次巩固都在 System Prompt 中给出完整的 Front Matter 示例。

3. **提取失败必须有告警**：每轮提取任务统计失败率。若 >1%，触发告警并暂停巩固任务。

4. **summary 和 hooks 的写入必须原子化**：先写临时文件，再 rename() 覆盖原文件。

#### 核心洞察

> "钩子回归内容本体，模板成为契约，脚本成为忠实的搬运工。"

> "不依赖奇技淫巧，只依赖清晰的边界和确定的契约。"

### 千问回答（待造物主验证）

**钩子位置确认**：

| 字段 | 对应概念 | 核心作用 |
|------|---------|----------|
| trigger_hooks | 精确匹配钩子（行为验证主战场） | 用户说了什么词，这张卡就该被拉入上下文 |
| semantic_hooks | 模糊语义钩子（兜底联想层） | 用户没说精确词但意图相关时的备选通道 |
| semantic_links | ⚠️ 这不是钩子 | 内部知识图谱的边，用于做梦/推理时的主动串联 |

#### 千问指出的四大核心矛盾

**矛盾一：触发钩子 vs 生命周期状态**

- **冲突本质**：高频读写字段与静态内容字段的物理耦合
- **问题**：trigger_hooks 每 3 天更新，access_count/last_accessed 每次检索都要更新，而 content 极低频变更。放在同一个文件里会导致频繁重写
- **后果**：Git 历史被无意义更新淹没，并发冲突概率上升，I/O 开销巨大

**矛盾二：AI Digest/Confidence vs Trigger Hooks**

- **冲突本质**：机器生成的主观评价与行为验证的客观事实争夺同一信任域
- **问题**：confidence 是 LLM 巩固时的主观快照，trigger_hooks 的有效性是靠 3 天行为数据算出来的客观事实
- **后果**：高置信度错误钩子难以淘汰，低置信度正确钩子在冷启动期被饿死

**矛盾三：关联钩子 vs 钢印时间链**

- **冲突本质**：网状图谱关系与线性版本树的结构错位
- **问题**：chain/parent_card_id 是严格的版本演化史，semantic_links 是动态的语义联想网。混在一起会导致 LLM 混淆

**矛盾四：情绪张力值 vs 标签/摘要**

- **冲突本质**：隐性计算参数与显性语义内容的边界模糊
- **问题**：tension_score 和 decay_rate 是系统控制变量，不应被 LLM 当作内容理解

#### 千问提出的三层分离方案

| 层级 | 包含字段 | 存储位置 | 更新频率 | 写入者 |
|------|---------|---------|---------|--------|
| L0: 身份与内容层 | seal_id, chain, parent_card_id, content, summary, cognitive_signature | 记忆卡 .md 文件 | 极低 | LLM + 签名器 |
| L1: 交互索引层 | trigger_hooks, semantic_hooks, tags, ai_digest | 独立 hook_index.db 或 .meta.json | 中频（3天统计） | 统计器 + 用户 |
| L2: 运行时状态层 | access_count, last_accessed, confidence, decay_rate, tension_score | 内存缓存/Redis | 极高频 | 系统自动 |

## 第48段：应用层与记忆层钩子置信度解耦

### 造物主确认（2026-06-27 00:38）
> "你说的是应用层和记忆层钩子置信度解耦吗？"

### 千问回答

**核心原则**：必须解耦。这不仅是架构分层的问题，更是认知系统能否保持"诚实"的底线。

> "谁有资格定义'这个钩子现在好不好用'？"

#### 两种置信度的本质对立

| 维度 | 记忆层置信度（LLM Confidence） | 应用层置信度（Behavioral Score） |
|------|----------------------------|------------------------------|
| **来源** | LLM 巩固时的主观判断 | 3天统计周期内的客观行为数据 |
| **性质** | 瞬时快照、易幻觉、不可验证 | 时间累积、可追溯、行为验证 |
| **作用域** | 仅作为 LLM 提案的"原始素材标签" | 决定钩子是否注入上下文的"唯一裁判" |
| **存储位置** | ❌ 不写入任何持久化字段 | ✅ 独立存在于 hook_index / .meta.json |
| **对检索的影响** | 零影响（被路由器/统计器丢弃） | 直接决定 hit_score 和晋升/淘汰 |

**核心铁律**：

> "LLM 输出的 confidence: 0.95 只是'运动员自称跑得快'，应用层的 hit_score 才是'计时器实测成绩'。系统只认计时器，不认自述。"

#### 解耦后的数据流

```
LLM 巩固
    ↓
输出 hooks + confidence
    ↓
路由器/准入网关
    ↓
🔥 丢弃 confidence，仅保留 term
    ↓
HookIndex 候选池（score=0）
    ↓
用户检索/反馈 → 行为日志
    ↓
3天统计器
    ↓
计算 hit_score
    ↓
├─ score ≥ 阈值 → ✅ 生效钩子
└─ score ≤ 0 → ❌ 淘汰
```

**红色阻断点**：路由器是置信度的"焚化炉"。LLM 无论多自信，过这道门后分数归零。

**绿色生成点**：只有统计器能产生真正的置信度，且该分数永远不回写到记忆卡本体。

#### 为什么这个解耦是关键？

**1. 防止 LLM 自我强化幻觉**

若不解耦，LLM 看到自己上次写的 confidence: 0.95，下次巩固时会倾向于保留甚至强化该钩子，形成"越自信越正确、越正确越自信"的认知闭环。解耦就是打破这个回音壁。

**2. 让"遗忘"成为可能**

LLM 的置信度没有自然衰减机制，一旦写高就永远高。而应用层 score 天然随时间衰减、随负反馈下降。只有解耦，记忆才能真正"代谢"。

**3. 支持人机主权分离**

用户可以手动添加钩子（无 LLM 置信度），也可以否决 LLM 的高置信度提案。若两者耦合，用户的操作就会被 LLM 的历史评分干扰。

#### 落地时的绝对禁令

1. **禁止在记忆卡模板中保留 confidence 字段**：连 `llm_confidence` 这种带前缀的字段都不要。它的存在本身就是诱惑。

2. **禁止统计器读取 LLM 置信度作为加权因子**：行为数据不足时宁可跳过更新，也不要用 LLM 分数填补空白。

3. **审计日志中可记录，但仅用于事后分析**：可以在 certification_log 里记一笔"LLM 当时声称 0.95"，但这只是为了未来优化 R2 prompt 用的诊断数据，绝不参与任何在线决策。

#### 核心洞察

> "我们不信任机器的自我评价，只信任行为的反复验证。"
