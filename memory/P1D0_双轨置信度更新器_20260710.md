## v1.1 核心改造：Facade 层（千问指出的关键问题）

> **千问诊断**：时间冷却掩盖了流程约束的真相。梦境管线有严格顺序，某些轨道在某些阶段本就不应该接受信号。

**改造前**：updater靠"3600秒冷却"假装处理了冷却问题，但流程约束是隐含的。
**改造后**：`process_dream_signal()` 作为唯一入口，阶段路由显式写死在代码里。

### 梦境阶段路由表

| 梦境阶段 | 允许的轨道 |
|---------|------------|
| T0 矛盾蒸馏 | `track_A`, `q3_eureka` |
| T1 连线引擎 | `track_A`, `q3_eureka` |
| T2 失谐放大 | `track_B` |
| T3 张力呼吸 | `track_A`, `track_B`, `q3_eureka`, `gc_feedback` |

### Facade 职责链

```
DreamSignalContext(phase, entry_id, track, ...)
    ↓
Step 1: 阶段路由校验（denied? → phase_mismatch）
    ↓ 通过
Step 2: 冷却期检查（skipped? → cooldown）
    ↓ 通过
Step 3: 数学计算（delegates to update()）
    ↓
ConfidenceUpdate(含拒绝原因 metadata)
```

### 查询接口（供子模块自检）

```python
# T0/T1/T2/T3 子模块发出信号前自检：
updater.is_track_allowed_in_phase("track_B", DreamPhase.T0)  # → False
updater.is_track_allowed_in_phase("track_B", DreamPhase.T2)  # → True
updater.get_allowed_tracks(DreamPhase.T3)  # → ['track_B', 'track_A', 'q3_eureka', 'gc_feedback']
```

## v1.0 核心成果（保持不变）

### 统一两套旧系统 + 梦境新需求

| 来源 | 旧公式 | 映射到 |
|------|--------|--------|
| `confidence_manager.py` Q3→Q1 | `Conf_new = Conf_old + Δ × Similarity` | 通路A（复用） |
| `gc_to_learning_adapter.py` GC反馈 | 记录信号，不改置信度 | 通路B（弱化×0.3）|
| 天赋实验梦境模块 | 通路A（拓扑激活） | 新增 |
| 天赋实验梦境模块 | 通路B（张力驱动） | 新增 |

### 双轨公式

**通路A**：`ΔC = α × (1 - C₀) × S_activation`（C₀越高越抗拒同化）
**通路B**：`ΔC = 0.15 + β × Tension_resolved`（固定基底+张力比例）

### 冷却期机制

- 同一节点同一轨道：3600秒（双轨独立冷却）
- 防止同一节点高频更新导致震荡
