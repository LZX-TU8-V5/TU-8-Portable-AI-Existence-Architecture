## 三、关键Bug及修复

### Bug 1: 缺少 `_transition()` 方法
**现象**: `AttributeError: 'WorkflowStateMachine' object has no attribute '_transition'`
**根因**: `request_start()` 调用了不存在的内部方法
**修复**: 添加完整的 `_transition()` 方法

### Bug 2: 状态文件路径跨测试污染
**现象**: TaskScheduler 测试之间互相干扰（同一 task_name 共享状态）
**根因**: 状态文件路径用 `hash(task_name)`，相同 task_name 共享状态
**修复**: 改用 `uuid.uuid4().hex[:8]` 作为唯一实例ID

### Bug 3: `import os` 缺失
**现象**: `NameError: name 'os' is not defined`
**根因**: task_scheduler.py 写入时手动加了 import，但原来没有
**修复**: 重写文件时确保 import 完整

### Bug 4: 测试断言逻辑错误（设计理解错误）
**现象**: `test_18_fuse_blocks_4th` 期望 n3 成功、n4 才熔断
**根因**: 对熔断设计理解错误——设计是 fuse_count≥3 时触发，
          即 n3 完成就触发（不是 n3 成功后再等 n4）
**修复**: 修正断言：`n1,n2` 成功；`n3` 触发熔断（assertRaises）

### Bug 5: `_save_state()` 父目录不存在
**现象**: `FileNotFoundError: No such file or directory: '...\src\_workflow_xxx.json'`
**根因**: 测试用临时目录，`src/` 子目录不存在
**修复**: `_save_state()` 开头加 `os.makedirs(os.path.dirname(path), exist_ok=True)`

### Bug 6: 文件被多次 edit 搞乱
**现象**: task_scheduler.py 有重复的 class 定义
**根因**: 多次 apply_patch 导致内容错位
**根因分析**: apply_patch 按 oldText 精确匹配，但文件中已有变化时匹配失败，
          最终重写了整个文件（write）解决

## 四、工程决策

### 决策1: 物理锚点记忆卡格式
```
anchor: "[GENE_SOURCE: src/xxx.py] [TAG: WORKFLOW] [ANCHOR: PHYSICAL]"
```
每步操作生成记忆卡，包含 card_id/step/action/detail/anchor。

### 决策2: 状态持久化 vs 内存
所有状态持久化到磁盘（JSON），支持断点恢复。
UUID 隔离确保跨测试不污染。

### 决策3: 熔断触发时机
设计确认：fuse_count≥FUSE_THRESHOLD(3) 时触发。
即第3节点完成时触发，不是第4节点。
解锁后 fuse_count 重置为 0，进入新周期。

### 决策4: 测试优先
先写测试用例，再实现功能。
测试覆盖：正常流转 + 禁止跳步 + 口令验证 + 熔断 + 隔离。

## 五、教训

### 教训1: 设计确认 > 直接实现
**事件**: Bug 4（测试断言逻辑错误）浪费了3轮调试
**教训**: 对设计细节有疑问时，先向用户确认再实现，不要猜
**编码**: "设计是 X 吗？" 先问清楚

### 教训2: 测试隔离要彻底
**事件**: UUID 隔离 bug，跨测试污染兜了一圈才发现
**教训**: 有持久化状态时，测试隔离需要 UUID 而非 name hash
**编码**: 涉及磁盘 I/O 的测试，用 UUID 做隔离键

### 教训3: apply_patch 要慎用
**事件**: 多次 apply_patch 导致文件损坏（class 重复）
**教训**: 大面积修改时，用 write 重写整个文件而非多次 patch
**编码**: 结构性修改（换 import、换 class）用 write > apply_patch

### 教训4: 测试设计要理解业务逻辑
**事件**: Bug 4 本质是对"熔断触发时机"这个业务逻辑的理解错误
**教训**: 写测试前先理解业务，写清楚"设计意图"注释
