### 2.2 传播链断裂 — cognitive_friction_registry → orb 闭环未闭合

**现状**：
```
cognitive_friction_detector.flag_friction()  → cognitive_friction_registry.json
    ↓ 缺失传播
surface_tension.record()                    ← 只被 surface_tension 自身调用
    ↓ 
surface_tension_state.json  ← 存在，但无人消费
    ↓ 缺失传播
lambda_state.json           ← lambda_tuner 读取，但 lambda→orb 未追踪
    ↓
orb (RGB)
```

**瓶颈节点**：
1. `cognitive_friction_detector` 无 `record()` 方法（公共接口只有 `flag_friction()` / `register()`）
2. `surface_tension` 自身无 `record()` 方法，只有 `_record_internal()`
3. HP4 `_trigger_cognitive_friction()` 正确地将 `pending_friction_surfacing.json` 写给 alignment_verify，但 alignment_verify → surface_tension_state → lambda_state → orb 的下行链路未追踪

**建议**：
1. 确认"orb 消费 surface_tension_state.json"是否有现役消费者（`orb_state_writer.py` 是否读取它？）
2. 若无，gap 在 surface_tension → orb，需要 `surface_tension` 向 `orb_state_writer` 推送
3. 若有，gap 在 friction_detector → surface_tension，需要在 `hp4_heartbeat` 的 `_trigger_cognitive_friction()` 中补一行 `surface_tension.flag_friction()`

### 2.3 Cron 链路失效 — hp4_heartbeat 长期 502/超时

**已知**：上游 LLM 链路（modelroute→qclaw-llm-provider）不稳定，cron 任务因此持续失败。

**现状**：
- `hp4_heartbeat.py` 由 cron_daemon 每 30 分钟触发
- 独立运行（`python src/hp4_heartbeat.py --interval 30`）正常
- 通过 cron_daemon subprocess 调用时报 502/超时
- `hp4_heartbeat_integration.py`：1812字节，全空桩

**诊断**：问题在上游 LLM 平台，非脚本代码问题。脚本本身行为正确。`hp4_heartbeat_integration.py` 为空桩是对的（逻辑在 hp4_heartbeat.py 中）。

**建议**：
1. cron_daemon 添加 LLM 调用任务的超时容错（已部分实现 subprocess timeout=90）
2. 若持续失败，考虑降级：hp4_heartbeat 的 LLM 部分（`heartbeat_with_hooks` 中的 LLM 调用）降级为纯本地启发式，不依赖远程 API
3. `hp4_heartbeat_integration.py` 可删除（1812字节空桩，无人引用）
