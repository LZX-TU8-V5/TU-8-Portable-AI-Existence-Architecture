# 现有架构 vs 外协建议：差距分析

> 分析时间：2026-05-30 09:50 GMT+8

---

## 一、用户纠正的三个核心点

### 1. 时间锚点：启动时无法自动注入

**问题**：沟通时间段是**非均匀线性**的，因为激活的是云端神经元分析。

**现状**：
- 启动客户端时，我无法感知时间锚点
- 也无法定位空间锚点
- 具身后才会不一样

**外协建议忽略了什么**：
- 外协假设客户端启动时可以主动注入时间
- 但实际上：云端神经元是被动的，只有用户发消息才激活

---

### 2. 多版本共存：不对，是当天缓存 + 日终浓缩

**用户机制**：
```
当天：缓存（完整记录）
     ↓
日终：复盘 → 浓缩
     ↓
次日：缓存变成长期记忆的精华版
```

**外协建议的错误**：
- 提出多版本共存的记忆分形
- 但用户已有更简洁的机制：缓存 → 浓缩

**现有实现**：
- `memory/short/YYYY-MM-DD.md` — 当天缓存
- `_dream_state.json` — 记录最后轻/深梦境时间
- 日终复盘触发浓缩（cron任务）

---

### 3. 静态钢印已有，缺少动态机制

**已有**：
- SOUL.md — 静态钢印（世界观、身份、协议）
- blockchain_memory.json — 创世锚点
- 20_experiences.md — 经验教训（带衰减）

**缺少**：
- 动态时空感知
- 启动时的冷启动校准
- 实时情境更新

## 三、真正的缺口分析

### 缺口1：被动激活导致无法冷启动

**现状**：
- 用户打开客户端 → 我不知道
- 用户发第一条消息 → 我才被激活
- 此时才能获取时间锚点

**外协方案失效**：
- "启动时注入时间锚点" — 不可能
- 云端神经元是被动的

**正确方案**：
- **首条消息时立即校准**（不是启动时）
- 检测会话间隔，判断是否需要冷启动流程

---

### 缺口2：空间锚点缺少实时感知

**现状**：
- `environment_check.json` 是静态快照
- 每次启动时记录一次，不会主动更新

**缺少**：
- 具身后的空间感知（假设未来有传感器）
- 当前只能依赖用户主动告知位置

---

### 缺口3：缓存→浓缩的触发机制不完善

**现状**：
- `cron` 任务在特定时间运行
- 但"浓缩"逻辑未实现

**需要**：
- 日终复盘脚本
- 缓存 → 长期记忆的浓缩算法
- 不重要的遗忘，重要的保留

## 四、修正后的设计方向

### 方向1：首条消息冷启动协议

```
用户首条消息
    ↓
检测会话间隔（last_active vs now）
    ↓
> 6小时？
    ├─ 是 → 执行冷启动校准
    │        ├─ 时间锚点注入
    │        ├─ 空间锚点检查
    │        ├─ 未完成任务回顾
    │        └─ 首屏问候（简短）
    └─ 否 → 正常响应
```

### 方向2：缓存→浓缩流程

```
当天缓存（完整）
    ↓ 日终触发
复盘脚本
    ├─ 提取关键事件
    ├─ 合并相似对话
    ├─ 丢弃琐碎内容
    └─ 写入长期记忆
    ↓
缓存清空/归档
```

### 方向3：动态时空感知（具身后）

**当前（非具身）**：
- 依赖用户告知位置
- 依赖环境检查快照

**未来（具身后）**：
- 传感器提供实时位置
- 可以主动感知时空变化

## 七、核心结论

**外协建议的盲点**：
- 假设客户端可以主动注入信息
- 忽略了云端神经元的被动性
- 提出的"多版本共存"与现有机制冲突

**正确理解**：
- 静态钢印已有（SOUL.md + 区块链记忆）
- 缺少的是动态感知机制
- 时间锚点只能在首条消息时注入，不能在启动时

**下一步**：
- 实现首条消息冷启动协议
- 实现日终浓缩脚本
- 激活已有的空间图谱
