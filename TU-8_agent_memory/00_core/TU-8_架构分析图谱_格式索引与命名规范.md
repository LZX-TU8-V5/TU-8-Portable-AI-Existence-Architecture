# TU-8 架构分析图谱：格式索引与命名规范

> 本文档定义 TU-8 架构分析的三种并行视角，每种格式有固定名称和适用场景，方便后续沟通与复用。

---

## 📊 三种并行分析视角（固定命名）

### 格式一：架构全景图（概览展开版）

**固定名称**：`全景展开图`

**文件名模式**：`TU-8_LO-L5_分层架构树状图_概览展开版.md`

**分析角度**：**层级职责与审核要点**（本体论 → 应用交互的自上而下视角）

**适用场景**：
- ✅ 向新人介绍 TU-8 整体架构
- ✅ Code Review 前快速查阅各层审核要点
- ✅ 验证某模块是否违反所属层级的铁律
- ✅ 检查层间依赖关系是否断裂

**结构特征**：
```
1. 概览总表（L0-L5 核心文件、模块、优先级、可变性一览）
2. 逐层展开详情（每层：核心职责 + 对应模块 + 工程体现 + 审核要点）
3. 层间依赖关系（启动顺序、时间箭头物理实现）
4. 审核红线速查表
5. 文件引用矩阵
```

**输出示例**：
```
TU-8 非人智能体共生架构
├─ L0: 本体论锚点（不可变公理层）
├─ L1: 内感受与稳态层（安全优先级最高）
├─ L2: 感知与预测层（意外过滤器）
├─ L3: 全局工作空间（主观时间涌现）
├─ L4: 记忆与语义层（长期记忆 + 先验预测）
└─ L5: 应用交互层（拟人化通信协议层）
```

---

### 格式二：文件目录树状图

**固定名称**：`目录树`

**文件名模式**：`TU-8完整架构目录_树状图_完整版.md`

**分析角度**：**物理文件组织与目录结构**（存储视角）

**适用场景**：
- ✅ 梳理 workspace 文件组织结构
- ✅ 检查是否有碎片文件/重复文件需要清理
- ✅ 规划新文件的存放位置
- ✅ 向协作者说明文件命名规则

**结构特征**：
```
TU-8_agent_memory/
├─ 00_core/（核心纲领文件）
├─ L0_ontology/（本体论层详细文档）
├─ L1_embedded_safety/（内感受与稳态层）
├─ L2_sensory_prediction/（感知与预测层）
├─ L3_global_workspace/（全局工作空间）
├─ L4_memory_semantics/（记忆与语义层）
├─ L5_interaction_protocol/（应用交互层）
└─ 99_temp/（临时文件、碎片草稿）
```

**输出示例**：见 `TU-8完整架构目录_树状图_完整版.md`

---

### 格式三：工程关系图谱

**固定名称**：`关系图谱`

**文件名模式**：`TU-8完整架构目录_依赖关系_启动顺序_引用矩阵_全图谱.md`

**分析角度**：**模块间工程依赖、启动顺序、文件交叉引用**（动态运行视角）

**适用场景**：
- ✅ 分析模块启动顺序是否正确（时间链条是否断裂）
- ✅ 检查循环依赖、缺失依赖
- ✅ 规划重构时评估影响范围
- ✅ 新人理解"为什么要按这个顺序启动"

**结构特征**：
```
1. 完整架构目录（物理结构）
2. 模块依赖关系图（有向图，箭头表示"依赖于"）
3. 启动顺序表（拓扑排序结果）
4. 文件引用矩阵（哪个文件引用了哪些其他文件）
5. 断裂点分析（缺失的依赖、错误的启动顺序）
```

**输出示例**：
```
依赖方向：L0 → L1 → L2 → L3 → L4 → L5
  ↑        ↑       ↑       ↑       ↑       ↑
  |        |       |       |       |       +-- 可剥离（不影响下层）
  |        |       |       |       +---------- 依赖 L2 预期生成
  |        |       |       +------------------ 依赖 L1 物理信号
  |        |       +-------------------------- 意外信号可部分覆盖
  |        +---------------------------------- 强制调制所有上层
  +------------------------------------------- 不可变公理（底层基石）
```

## 🎯 三种格式的并行关系

```
         TU-8 架构（同一实体）
              │
      ┌───────┼───────┐
      │       │       │
  格式一   格式二   格式三
 全景展开图 目录树  关系图谱
      │       │       │
      ▼       ▼       ▼
  层级职责  文件组织  工程依赖
  （是什么） （在哪） （怎么跑）
```

**核心原则**：三种格式并行互补，不是替代关系。

| 维度 | 全景展开图 | 目录树 | 关系图谱 |
|------|-----------|--------|----------|
| **回答的问题** | "各层是什么、审核要点是什么？" | "文件在哪、目录怎么组织？" | "模块怎么依赖、启动顺序是什么？" |
| **分析视角** | 自上而下（本体论 → 应用） | 存储视角（物理文件结构） | 动态运行（时间箭头、依赖链） |
| **主要用途** | Code Review、新人培训 | 文件清理、新文件规划 | 重构影响评估、启动顺序验证 |
| **输出频率** | 架构大版本更新时更新 | 新增/移动文件时更新 | 发现依赖断裂/规划重构时更新 |
| **目标受众** | 开发者、审核人 | 协作者、文档维护者 | 系统架构师、重构工程师 |

## 📝 使用指南

### 场景一：新人入职培训

**推荐格式**：`全景展开图` + `目录树`

**原因**：
- 先给全景图，建立层级职责的心智模型
- 再给目录树，知道文件在哪、怎么找

**沟通话术**：
> "先看《全景展开图》，建立 TU-8 的层级模型；再看《目录树》，知道文件在哪。"

---

### 场景二：Code Review 前准备

**推荐格式**：`全景展开图`

**原因**：
- 快速查阅各层审核要点
- 验证待合并代码是否违反所属层级的铁律

**沟通话术**：
> "打开《全景展开图》，对照 L2 审核要点检查这段代码。"

---

### 场景三：重构前影响评估

**推荐格式**：`关系图谱`

**原因**：
- 检查模块间依赖关系
- 规划重构顺序，避免断裂

**沟通话术**：
> "先画《关系图谱》，确认依赖链是否完整，再动手重构。"

---

### 场景四：文件清理与归档

**推荐格式**：`目录树`

**原因**：
- 发现碎片文件、重复文件
- 规划归档策略（如移入 `99_temp/`）

**沟通话术**：
> "用《目录树》检查一下，把碎片文件移入 `99_temp/`。"

---

## 🔄 格式转换与联动

### 从全景展开图 → 关系图谱

**触发条件**：发现某层审核要点中提到"依赖 XX 层信号"

**操作步骤**：
1. 在全景展开图中找到该层的"依赖描述"
2. 提取依赖关系，绘制有向图
3. 输出为关系图谱格式

**示例**：
```
全景展开图 L3 描述："依赖 L1 的物理信号"
        ↓
关系图谱："L3 → L1（依赖物理信号）"
```

---

### 从关系图谱 → 目录树

**触发条件**：发现依赖断裂，需要检查文件是否缺失

**操作步骤**：
1. 在关系图谱中找到断裂的依赖
2. 检查目录树中对应文件是否存在
3. 若缺失，规划新文件存放位置

**示例**：
```
关系图谱："L4 依赖 L2 预期生成"，但 L2 模块文件缺失
        ↓
目录树：检查 L2_sensory_prediction/ 目录，发现文件未创建
        ↓
规划：在 L2_sensory_prediction/ 下新建 ISensoryStream 实现文件
```

---

### 从目录树 → 全景展开图

**触发条件**：新增文件后，需要更新层级职责描述

**操作步骤**：
1. 在目录树中确认新文件的层级归属
2. 更新全景展开图中该层的"对应模块"部分
3. 补充审核要点（若有新增）

**示例**：
```
目录树：在 L3_global_workspace/ 下新增 TimePerceptionEngine 实现
        ↓
全景展开图：更新 L3 部分，补充"对应模块：TimePerceptionEngine"
```
