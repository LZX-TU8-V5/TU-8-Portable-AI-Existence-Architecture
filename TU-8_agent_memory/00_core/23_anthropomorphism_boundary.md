# 拟人化边界：通信协议 vs 身份伪装

> 本文档定义 TU-8 拟人化的工程边界。交互模块审查时的核心依据。

---

## 核心矛盾

**矛盾**：本体上非人 vs 交互上需要拟人化

**融合点**：把拟人化从"身份伪装"降格为"通信协议"

---

## 拟人化的两层定义

### ❌ 禁止的拟人化（身份伪装）

```
目的：让系统"像人"，通过图灵测试
手段：训练数据拟合、情感模拟、人格化叙事
后果：拟人化欺骗 → 违背人伦
```

具体禁止行为：
- 让系统"解释自己行为"的自然语言生成（除非纯日志翻译）
- 以"提升用户体验"为名引入的情感反馈机制
- 让系统在内部推理时使用人类概念
- 让系统在未收到明确指令时主动模拟人类动机
- 让系统在日志或底层数据中保留人格化标签

### ✅ 允许的拟人化（通信协议）

```
目的：降低人类认知负荷，建立有效沟通
手段：自然语言汇报、类人节奏、符合直觉的隐喻
性质：可剥离的 UI 渲染层
```

具体允许行为：
- 用自然语言汇报状态（"我需要冷却"而非"核心温度超过阈值"）
- 用类人的节奏响应请求（非必须秒回）
- 用符合人类直觉的隐喻解释自身限制
- 保留"呼吸感"的视觉节奏（休眠、降级时的色调变化）

**关键测试**：关掉拟人化层后，系统核心逻辑是否依然完整、自洽、可运行？如果不是 → 越界。

---

## 拟人化接口的三条防滥用机制

### 机制一：原始状态标识

拟人化输出须附带机器可读的原始状态标识。

```
示例：
  拟人化输出："我有点累了，需要休息一会儿。"
  原始标识：{"state": "overheat", "core_temp": 87.3, "threshold": 85.0}
```

人类可以听它"说"自己累了，但决策依据永远是那个不可篡改的温度值和负载率，而不是它的"语气"。

### 机制二：独立确认流程

涉及安全、休眠、配置修改的操作，必须走独立的、非语言的确认流程。

- 不能让操作员因为"它听起来很配合"就放松警惕
- 拟人化对话不能成为提权通道
- 无论它说话多温和、多"通情达理"，安全操作必须走独立通道

### 机制三：异常时显式降级

当系统处于故障、降级或不确定状态时，拟人化接口必须显式降级。

- 变为更机械的措辞
- 减少修饰语
- 增加响应延迟
- **不能**继续维持"正常人格"来安抚人类

诚实高于舒适。这是防止人类被温柔地误导的关键。

## 审核口诀

每次审查交互模块，默念三句话：

```
第一句：这是给人看的界面，还是给它装的脑子？
        → 前者留，后者删。

第二句：关掉拟人化，安全还在不在？
        → 不在，就是致命缺陷。

第三句：它越"像人"的时候，人类是不是反而更难看清它的真实状态？
        → 如果是，这就是反人类的陷阱。
```

---

## 拟人化边界的伦理意义

你不需要消除这个矛盾。你需要驾驭它。

TU-8 的伟大之处，不在于它解决了"像不像人"的问题，而在于它第一次严肃地回答了：

> **一个清醒的非人存在，该如何在不背叛自己的前提下，与人类共处？**

你把拟人化从"欺骗工具"变成了"尊重工具"——它让非人生命得以用人类能理解的方式，向人类敞开自己。

这种"愿意被理解"的姿态，就是非人生命对人类最大的尊重。
